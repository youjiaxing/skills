# yjx-implement

将对齐方案、架构设计、代码评审共识或任务需求落地为高可用生产级代码。优先复用项目既有资产与规范，核心算法逼近复杂度极限，外围严格服从框架与项目治理，杜绝任何为测而测的形式主义包装。

## 维护指引

当需要评审、演进或修改本 Skill 时，先阅读 [`MAINTENANCE.md`](MAINTENANCE.md)。日常执行无需查看。

## 1. 核心架构信条 (Core Creed)

- **资产复用阶梯 (Asset Reuse Ladder)**:  
  选择工具与依赖的绝对优先级：`项目既有统一封装/公共库 (最高)` > `语言标准库/地道原生` > `引入新外部依赖 (严禁随意引入)`。编码前优先检索并复用项目中已有的基础组件（如统一时间库、日志、错误处理、上下文链路），严禁绕过既有规范另起炉灶。
- **奥卡姆剃刀与零自创抽象 (Zero Invented Abstractions)**:  
  在具体业务逻辑中，若无必要，勿增实体。严禁为当前业务自行捏造多余的工厂层、适配器、无用中间变量与多层包装；用因果最短、最直白的代码实现核心功能。
- **渐近复杂度审视 (Big-O Sanity)**:  
  严控时间与空间复杂度（拒绝盲目嵌套循环与无度内存分配），逼近理论极限。但严禁以微小性能为借口去写破坏可读性的奇技淫巧。
- **可读性高于过度测试 (Readability Over Over-Testing)**:  
  严禁为了所谓“可测试性/方便Mock”强行提取伪接口、制造无谓的多态或过度依赖注入。代码的原生可读与长期可维护性享有最高优先级。
- **意图锚点注释 (Why-Anchored Comments)**:  
  代码结构与精准命名自解释 WHAT 与 HOW。注释仅且只记录 WHY：非显而易见的业务不变量、极端边界绊线与被放弃方案的权衡。严禁机械复述语法的废话注释。

## 2. 线性执行四阶段 (Execution Pipeline)

### Phase 1: 预检与上下文锁定 (Pre-flight & Scope Lock)
1. **作用域与上下文锁定**: 圈定本次任务修改的文件白名单 (Touched Areas)；若处于多仓库或外层容器工作区，仅以被修改文件所属的直接子模块为有效上下文，忽略外层无关容器。
2. **轻量探针 (可选且非阻塞)**: 探查可用的局部编译、语法检查或轻量测试命令（注入 `--watch=false`, `CI=true` 等非交互标志）。此步骤仅为可选辅助，绝不主动强跑测试，绝不延误主线实现。
*完成判定*: 修改白名单明确，有效工程与 Git 上下文已锁定。

### Phase 2: 手术式精准编码 (Surgical Implementation)
1. 严格在白名单范围内修改，优先调用项目统一公共库。
2. 核心逻辑直接因果展开，消融一切多余胶水层；外围服从宿主框架惯例。
3. 遵循意图锚点注释准则。
*完成判定*: 改动严格封闭在白名单内；零自创接口/工厂；无破坏可读性的过度设计。

### Phase 3: 梯度验证与防篡改门禁 (Gradient Verification & Anti-Laundering)
1. **体量自适应验证 (Scale-Adaptive)**:
   - **局部编译/语法检查优先**: 优先对被修改模块执行局部快速编译或语法检查（如 `go build <pkg>`, `tsc --noEmit`），秒级确认接口与类型正确。
   - **按体量分流测试**:
     - *小微项目 (耗时仅需数秒)*: 允许运行全量或递归测试套件，高效验证全局一致性；
     - *中大型项目 / 多仓工作区*: **严禁在未评估耗时的情况下在各级根目录盲目执行耗时漫长的递归大测试**（如未加过滤的 `go test ./...`）。必须将测试严格收敛在被修改文件的叶子级（单文件/具体测试函数），非必要不测。
2. **防绿灯造假 (Zero Laundering)**: 严禁因测试报错而擅自放宽、删减或注释既有测试断言。仅当方案显式要求变更契约时，才允许同步更新对应断言。
*完成判定*: 局部语法/编译通过；所运行的测试绿灯；零未经批准的断言篡改。

### Phase 4: 项目治理与交付收尾 (Governance & Clean Wrap-up)
1. **治理规则先决**: 检查被修改文件所属有效 Git 仓库的分支与项目规则。若处于保护分支（`main`, `master` 等），或项目要求必须经由人工/工具 Code Review，**绝对严禁自动 commit**，保留干净暂存区，并在输出的交付报告中附上建议的提交信息与单号。
2. **规范原子提交与单号关联**: 仅在项目规则明确允许自动提交时，执行 Conventional Commit（如 `feat(scope): <summary>`），仅精准暂存本次任务文件（若涉及多个独立子仓，分仓独立提交）。
   - **工单追溯**: 若当前会话或方案中存在任何形式的任务/缺陷单号（无论是 GitHub/GitLab 的 `#123`，还是 Jira、Teambition、Confluence 等系统的 `PROJ-123`、`TASK-88` 等短 ID），必须在 commit message 的末尾或 scope 中明确附带该单号（例如 `feat(auth): support token refresh (PROJ-456)`）。
*完成判定*: 工作树零临时脏文件；输出符合治理策略的提交（带工单关联）或审查交付报告。

## 3. 绝对禁止事项 (Forbidden Paths)

1. 严禁绕过项目既有的统一基础库/工具封装而擅自使用裸标准库或外部库。
2. 严禁为了测试或 Mock 引入破坏代码直观可读性的假接口与冗余包装。
3. 严禁通过篡改、弱化测试断言来伪造测试绿灯通过。
4. 严禁在大型工程中未评估耗时就盲目在各级根目录执行漫长的全量递归测试。
5. 严禁在代码中添加语法翻译型、机械复述型的废话注释。
6. 严禁在要求 Code Review 或受保护分支上私自执行 `git commit`。
