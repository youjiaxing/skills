# yjx-upstream-review

评估上游变化解决的问题及其对本仓库的启发，交付吸收建议并维护核查进度。是否吸收由用户决定。

## 权限与职责

调用授权读取本地与公开上游、创建任务临时材料，以及更新实际完成的来源核对和评估记录。默认交付建议；修改现有 skill 的运行规则、安装或更新第三方 skill、提交、推送及外部写入需要另行执行授权。用户明确要求只读时，记录更新也只作为建议交付。

本入口从上游变化寻找改进；`yjx-retro-skill` 从实际任务及用户纠正寻找改进，两者不互相强制调用。需要编辑 Agent 文档时，通过宿主发现机制定位并读取 `writing-for-agents`；不可用时报告依赖缺失，保留已完成的调查与建议。

## 1. 确定仓库、范围与证据

在当前工作目录执行 `git rev-parse --show-toplevel`，确认发现的项目根就是本入口所属仓库；不在其他项目或用户目录直接运行。读取根 `AGENTS.md`、本入口的 [维护记录](MAINTENANCE.md)，并检查 Git 状态，区分本次工作与既有改动。从子目录调用时统一使用仓库根路径。

默认覆盖本仓库已知的启发来源。读取根 README 的演进映射、各本地 skill 的 `MAINTENANCE.md`、来源声明和必要的 Git 引入历史，建立临时的“上游仓库 / 相关路径 → 本地 skill”映射。同一来源只获取一次；允许一对多、多对一。用户指定来源或 skill 时限制本次范围。

区分派生、概念启发和运行时依赖。安装锁文件、同名文件及普通链接只能提供线索，不能独自证明派生关系。没有精确旧版本时保留未知；不把本机已安装版本当作历史上游基线，也不把当前上游版本倒填为最初参考版本。来源冲突时调查，无法解决则单列缺口。

**完成条件：** 范围内每个已知来源有明确的本地承接对象或待核实说明；已有来源记录、仅核对来源的快照、实际完成的行为评估和待讨论建议已区分。

## 2. 固定版本并检查变化

以公开上游源码、提交和发布说明为一手证据。固定本次目标 commit，后续读取该版本，避免检查中途分支移动。尊重上游实际默认分支，不假设名为 `main`。

对已知对应路径精读变更，同时轻量扫描该上游仓库自上次扫描以来的新增、删除、改名及重大流程调整。扫描到的新思路可以建议给其他本地 skill；说明联系和具体价值后才深入，不扩成无界生态搜索。不因上游删除就删除本地能力；重命名或迁移要追踪新路径。

按已记录的证据选择比较方式：

- **有已评估版本：** 比较它与本次固定版本的相关路径增量，再核对当前本地实现和维护取舍。
- **只有来源快照、没有行为评估：** 快照可用于提取上游增量，但首次仍需评估当前相关能力与本地的对应关系；不能把快照之前的能力声称为已评估。
- **没有可信版本：** 建立当前对照点并评估当前能力；历史提交只能提供候选变化，不能称为准确的本次更新差异。

若提交不可获取、历史被改写或路径消失，说明证据边界；继续可核实的独立范围，不推进失败部分的检查版本。仓库扫描与具体路径评估分别界定覆盖，不能用一个新 HEAD 声称全仓已精读。

多来源或大量独立证据确有并行收益时，可委派有界只读调查。Start every subagent with a fresh context window (do not fork the current conversation). 交接只含问题、固定版本、路径、允许的临时写入范围和完成条件；禁止继续委派，由主代理综合判断、复核决定性证据和修改本地文件。按宿主要求选择工具；无可用子代理或调用失败时，主代理直接完成可覆盖的范围并披露限制。

**完成条件：** 每个完成检查的来源具有可复现的目标版本、比较依据和覆盖范围；事实、候选历史及证据缺口均有定位。

## 3. 判断是否值得吸收

先理解上游变化针对的触发条件、问题和预期结果，再查看当前本地 skill 的真实规则、脚本及明确保留的取舍。逐项判断：

- **建议吸收：** 本地存在具体缺口，或可得到有依据的能力、可靠性或维护收益。给出目标 skill / 文件、最小修改方向、证据、收益、成本和适用边界。能直接采用的明确改进与需要讨论的行为、权限或职责变化分开说明。
- **已有覆盖：** 指出本地对应位置，避免重复叠加规则。
- **保留本地取舍：** 说明不适用、收益不足或与已确认需求冲突的原因。上游不天然优于本地；只有新证据涉及原取舍的依据时才提出重开讨论。
- **待核实：** 列出缺失事实及其会改变的判断；不把推测列为可直接实施项。

纯文案、封面和无关发布调整通常无需吸收。跨文件同义规则优先归并到既有权威位置，避免为每个上游补丁新增禁令或重复门禁。涉及模型读图的候选改进须遵守仓库对 `yjx-image-reading` 的依赖要求，不在本入口复制图像观察流程。

**完成条件：** 每项实质相关变化有上述去向；建议具备本地落点与实际价值，无建议也是有效结果。

## 4. 交付建议并维护进度

先核对结论与来源、范围和本地事实一致。按价值排序展示建议；每项让用户无需阅读原始 diff 就能判断上游解决了什么、本地如何受益、代价是什么。附关键提交或源码链接，简述已有覆盖和不采用原因，列出未完成范围。不要把整仓 diff 或原始研究笔记当作结论。

记录沿用本地 skill 的 `MAINTENANCE.md`，不存在时可仅为本次来源和评估记录创建该文件，不建立平行的永久研究档案：

- 记录日期、来源与路径、比较版本和本次固定版本、实际核查范围、结论去向及必要证据链接。保留原有历史和未知项。
- **已评估与已吸收分开。** 完成评估后可以推进该范围的评估版本；待讨论建议仍保留为待定，后续检查先回看，不能因版本推进而丢失。部分完成只记录已覆盖路径，未覆盖部分保留原进度。
- 用户之后同意并实际实施、验证的改动，才由实施步骤记录为已吸收；本次调用不会自动进入实施。
- 仓库级轻量扫描的版本、覆盖范围及尚未对应本地 skill 的候选，记录在本入口 [维护记录](MAINTENANCE.md) 的扫描记录中；不替代各 skill 的行为评估记录。

临时克隆、比较和调查笔记使用根 `tmp/research/<本次任务标识>/`；结束时先将仍需人工决定的建议及关键证据落入上述维护记录，再仅清理本任务材料。用户要求只读时在回复中交付待定项和证据。无法取得的证据或记录写入失败必须在结果中说明。

**完成条件：** 结论、实际更新的记录和未完成范围已交代；待定建议可续接；临时材料已定向清理。用户只获得吸收建议与核查记录，没有未经授权的运行规则变更或自动更新。
