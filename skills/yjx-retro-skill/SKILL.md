# yjx-retro-skill

由用户手动触发。主会话主持复盘，从本次实际损失与用户每一次纠正行为出发，寻找值得优化的已有 skill 问题、值得孵化或拆分的新 skill 机会，以及 Agent 协作文档改进点，而不是对指令逐条挑错。默认只调查并提出建议；新建、修改、拆分、安装、提交 skill 或操作外部系统属于另行授权的实施。

## 1. 确定证据范围与分工

默认复盘当前会话中已完成的实质任务，截止本次复盘调用前；用户指定其他会话或任务时按指定范围。区分多个任务及其依赖，避免将复盘过程本身混入被复盘任务。

主代理负责理解用户意图、安排调查、综合归因和交付建议。按被复盘任务的原始对话是否仍保留在当前上下文中分流：

- **当前上下文完整覆盖被复盘任务（未被压缩摘要替换）：** 直接将当前上下文中的用户消息、加载的 skill、工具调用与输出作为主要证据，配合对相关 skill 文件、任务产物或 Git 状态的必要只读核验。全程由主代理单代理完成取证、归因、筛选与交付前核查；**不读取 [会话记录取证](references/session-evidence.md)，不查找或读取当前会话的磁盘原始记录（如 session JSONL），不启用取证子代理或独立评审子代理**。即使更早的无关任务曾被压缩，只要被复盘任务本身的原始对话仍在当前上下文中，仍走本分支。不把缺少宿主显式“未压缩”标记当作状态未知；若当前上下文中个别工具输出被截断或局部证据不足，直接记为证据缺口并限制结论范围，不借此回查磁盘会话日志或开启子代理。
- **被复盘任务在当前上下文中已被压缩摘要替换（含复盘前已替换或复盘期间被压缩），或用户指定复盘其他会话：** 当前上下文中仍保留的原始消息与工具结果可直接作为证据；对已被压缩摘要替换的区段或外部目标会话，读取 [会话记录取证](references/session-evidence.md) 定位磁盘原始会话记录并固定截止点，压缩摘要仅用于定位线索。将需要补读磁盘原始会话记录的只读工作交给上下文隔离（`fork_turns: "none"` 或平台等价机制）的子代理（Start every subagent with a fresh context window (do not fork the current conversation).），传入本 skill、目标记录定位、用户目标与约束、明确的调查范围及返回要求；子代理分段读取并仅返回带定位的精简证据包，主代理按定位回查关键原文，不把整份日志载入主上下文。若宿主无法使用子代理，主代理说明限制并自行分段读取必要区段。

按本次目标建立轻量时间线与覆盖记录：用户要求、**用户的每一次纠正行为**（包括显式纠偏、推翻或修正 Agent 输出与做法、中途叫停不当动作；普通方向切换先核实是否属于对 Agent 偏差的纠正）、实际加载的 skill（若本次未使用任何 skill 则明确记为无，同时利用已知可用 skill 列表与目标仓库相关范围识别疑似可承接职责或漏触发的候选 skill，不无故全盘扫描无关目录）、关键工具结果、失败和返工、最终交付及其核验。当前上下文分支直接使用上下文中的消息顺序、工具调用或事件定位；磁盘取证分支使用记录路径与行号或稳定消息 ID。记录已覆盖区段与缺失、截断、仅有摘要的区段。按时间线覆盖任务，再围绕疑点检索；仅搜索错误关键词不能证明已检查整个任务。

完成条件：能定位被复盘任务、实际使用的 skill（或确认本次未使用任何 skill）、已覆盖区段内的全部用户纠正行为和证据范围；无法还原的部分明确标为缺口。无论本次会话是否实际使用了已有 skill，均综合整个会话的任务过程与用户纠正进行复盘：主责轨道覆盖 **Skill 层建议（本次已用 Skill 优化、已有未调用 Skill 补强、新建或拆分 Skill 提议）**；超出 Skill 层职责但经核实有价值的项目知识或协作体验问题，按第 3、4 节其余三层标准分流。

## 2. 逐次复盘用户纠正与实质问题归因

除从错误、误解、返工、不必要操作成本和影响使用的交付缺口寻找候选问题外，必须对已覆盖区段内**用户的每一次纠正行为**逐一复盘。必要时按疑点只读核验相关产物、原始来源、脚本或外部实际状态，不完整重做任务。读取外部状态仍需现有访问权限；核验不能附带写入或重新执行日志中的动作。

评估用户纠正时遵循这一准则：**并非用户每一次纠正都是正确、合理的，但大概率符合用户偏好。** 将“纠正是否合理”与“是否固化为通用规则”解耦，先结合当时上下文、客观事实与任务目标逐次判定合理性：

- **合理（有道理 / 符合用户真实偏好或当次合理意图）：** 用户指出了真实的执行偏差、理解错位、低效默认行为、过严/缺失门禁，表达了跨场景协作偏好，或结合当次任务情境作出了合理的指令纠偏。所有判定为合理的纠正，均必须进一步追问“当时为什么会走到需要用户纠正这一步，后续如何从机制上避免再次发生”。
- **不合理（受当时信息偏差或事实误判影响）：** 经客观事实与上下文核验，用户在当时信息不完整或误判客观状态的情况下给出的纠正，按其修改会导致错误或退化。
- **证据不足无法判断：** 因上下文截断、外部状态不可考等原因无法核实纠正合理性或因果，保留为待核实缺口，不强行定性。

对每个候选问题及每次合理纠正核实：发生了什么、偏离哪项用户目标或稳定偏好、造成什么实际影响、当时适用的 skill（或可承接该职责的已有候选 skill）指令及其职责定位与准入边界是什么，以及如何从机制上避免同类问题再次发生。尽可能核实执行时版本与当时可用状态；当前文件和事后 Git 修改不能直接代表当时版本或当时可用性。明确区分以下原因，可记录共同原因：

| 原因 | 处理 |
| --- | --- |
| 本次已使用 Skill 缺口、冲突、默认行为与用户高频偏好相反、过严或缺少适用条件 | 分析如何避免复发，检查最小通用修改能否改善同类任务 |
| 已有但本次未调用 Skill 的触发或内容缺口（已知可用列表或目标仓库相关范围内存在职责匹配的已有 skill） | 先只读核验该候选 skill 的 `SKILL.md` 正文与职责边界：若证实任务执行时已可用且允许调用，归因为触发指针（`description`）/入口导航缺口或执行漏调；若无法证实当时已可用（仅确认当前存在），不倒推为历史漏调缺陷，仅将其作为**当前优先复用并承接该职责的已有 Skill 优化目标** |
| 可复用按需工作流缺失或现有 Skill 职责过载（新建或拆分 Skill 候选） | 当某套多步工作流、专项排查/操作规程或领域方法具备跨任务复用价值，因仅在特定场景按需触发而不宜常驻 `AGENTS.md`，且经核验现有相关 skill 正文确认无职责匹配项（或塞入现有 skill 会导致职责异质/过载）时，转入第 3、4 节的“新建或拆分 Skill 提议” |
| 项目内文档 / Spec / 知识库缺口（属当前项目的运行时机制事实、架构决策或特定业务模块的非显然边界） | **不得假设项目内一定存在 Spec/知识库体系**。仅当已有上下文、项目 `AGENTS.md` 或已加载 skill 证实该项目维护了对应文档体系时，按该项目自身的收录标准评估是否转入第 3、4 节的“项目内文档/Spec 建议”；若确认不存在或未达其收录标准，则不生成该项目文档建议，继续按其余各层标准评估其他适用落点；若证据不足无法确认该项目文档体系或门槛，记为“项目文档/Spec 层待核实”且不无故扩大全仓扫描 |
| 项目/工作目录级或用户级全局协作层缺口（属仓库/目录级持续约束，或跨项目的用户个人偏好与通用 Agent 体验机制） | 不写入 Skill 层；按作用域区分“项目/工作目录级 `AGENTS.md`”与“用户级全局 `AGENTS.md` / 个人全局提示词”，转入第 3、4 节对应分流建议 |
| agent 未遵守已有明确规则 | 记录执行偏差；只有证据显示规则难以发现、冲突或无法落实时才进一步建议修改规则，否则作为“合理但无需新增通用规则”结案 |
| 工具、环境或访问限制 | 指出能力边界；仅在 skill 的能力判断或降级流程有问题时建议修改它 |
| 单次任务特例（单次事故口径、当次临时改主意、随本次修复/结单即失效的一次性问题，或经评估不满足上述任何适用层准入条件的局部细节） | 单次特例不等于用户当次纠正不合理，但直接排除在规则、Skill 与文档修改建议之外，不将一次性防错补丁或个案流水写入任何层级 |
| 原因未知或证据不足 | 列明缺失证据及其对判断的影响，不当作已确认缺陷 |

对照已有保护措施和反证，检查问题是否已在后续版本修复。保留有价值的实际经验，但已解决的问题不再重复建议修改。Git 可辅助定位演进，不能单独证明会话因果或优化效果。

## 3. 筛选最小优化与四层落点分流

只有同时具备具体证据、实质影响（或合理的用户纠偏信号）、可解释的机制归因，以及在**目标承载层适用范围内**的持续复用价值，才进入正式优化建议。一次严重问题或一次有道理的用户纠正即可作为触发信号，不要求反复发生。

所有建议均必须**剥离单次事故表象、具体报错值、当次对话表面原话及随本次修复即失效的一次性 Bug**。按**作用域**、**信息性质**与**上下文常驻成本**（优先落入按需加载层，不无故上浮到每轮常驻加载层），将防复发建议按以下四层评估并对齐各自的去特例化标准：

1. **Skill 层建议（主责轨道，按需加载）：**
   - **已用 Skill 优化 / 已有未调用 Skill 补强：**
     - **适用范围：** 属于本次已使用 skill，或经在已知可用列表与目标仓库相关范围内只读核验 `SKILL.md` 正文后确认可承接该职责的已有未调用 skill 的工作流步骤、触发指针（`description`）、检查点、分流路由或能力降级规则。不得凭空臆测未核实的“已有 skill”；无法证实任务执行时已可用的 skill 仅作为当前优化目标，不倒推为历史漏调。
     - **去特例化要求：** 在该 skill 覆盖的任务范围内跨模块、跨工单通用（通用 skill 须剥离具体业务模块；若保留落实规则所必需的领域入口，须符合该 skill 自身的职责定位与准入边界）。
   - **新建独立 Skill 或从已有 Skill 拆分提议：**
     - **准入条件：** 必须同时满足：（a）具备跨任务重复触发信号与实质减负价值，排除一次性脚本或单次任务流；（b）属于特定场景按需加载的多步流程、专项规程或领域方法，不宜常驻 `AGENTS.md` 消耗每轮上下文；（c）在已知可用列表与目标仓库相关范围内对疑似相关候选 skill 只读核验 `SKILL.md` 正文后，确认无职责匹配的现有 skill，或现有 skill 已过载需按调用时机/序列边界拆分（若受限于可见范围无法完全排除外部重叠，须在提议中标注“与现有 Skill 重叠关系待核实”）。
     - **交付边界与去特例化要求：** 剥离单次任务表象，抽象出通用触发条件与职责边界；复盘阶段因具体边界尚需与用户讨论并获用户授权才允许创建，**仅输出“新 Skill 概要卡片”提议**，不直接生成完整 `SKILL.md` 正文。
2. **项目内文档 / Spec / 知识库建议（跨出 Skill 层的分流轨道，按阶段/模块加载）：**
   - **适用范围：** 当前项目内跨任务复用的运行时机制事实、架构决策（ADR）、工程规范或特定业务模块的非显然易错边界。**严禁假设项目内一定存在 Spec/知识库体系，也严禁凭空要求新建该体系。**
   - **去特例化与准入要求：** 仅在已证实该项目存在对应文档体系时启用；允许保留该项目对应业务模块或运行时机制的真实领域身份与关键边界，但必须剥离单次事故流水，且严格符合该项目自身规定的文档收录标准与维护权限（如“难以从代码轻易恢复、相对稳定、能减少后续成本”）。若项目无此体系或未达其门槛，仅排除本层建议，不提前短路对其他层的评估；若受限于当前证据无法确认体系存在性、收录门槛或目标位置，仅记为“项目文档/Spec 层待核实”。
3. **项目/工作目录级 `AGENTS.md` 建议（跨出 Skill 层的分流轨道，当前仓库/目录常驻）：**
   - **适用范围：** 在当前仓库或工作目录（含子目录 `AGENTS.md`）适用范围内需要持续遵守的协作约束、仓库拓扑、编译测试边界、提交规范或顶层 Skill 导航入口。
   - **去特例化要求：** 剥离单次事故表象，允许保留落实该约束所必需的仓库、子仓或目录身份，确保在该目录适用范围内持续有效。
4. **用户级全局 `AGENTS.md` / 个人全局提示词建议（跨出 Skill 层的分流轨道，所有项目常驻）：**
   - **适用范围：** 跨所有项目复用的用户个人沟通偏好、问答格式、工具优先级、子代理协作策略等用户级通用规则（如 `~/.codex/AGENTS.md`、`prompts/shared/`）。
   - **去特例化要求：** 必须剥离具体项目、仓库与业务特征，确保跨项目通用。

优先选择解决机制的最小改动：优先复用并最小修改现有 skill（澄清适用条件、补强触发指针、调整默认动作或导航、消除冲突、删减或放宽约束、或为机械步骤补充确定性工具），仅在现有 skill 无法合理承载或确需拆分减负时才提议新建/拆分 skill。比较改动带来的执行成本、上下文负担、维护成本和对其他场景的影响。区分“无实质收益的表面字眼挑剔或目录整齐偏好”与“曾引发用户合理纠正、能稳定减少协作摩擦的用户偏好”：前者不作修改，后者在完成对应层级的去特例化后纳入建议。

预期收益是推断，不能表述为已验证效果。缺失证据会改变归因或修改方向时，保留为待核实线索；不要凭不确定性增加通用规则。

## 4. 核查与交付

交付前，主代理核查每项候选（含 Skill 层建议与跨出 Skill 层的各层分流建议）的证据、合理性核验、归因、对应承载层的去特例化程度、职责边界及修改影响，解决有证据的反驳与遗漏，剔除仍绑定单次事故特征或不满足目标层准入标准的候选。当前上下文完整分支由主代理直接完成核查，不启用独立评审子代理；仅在“被复盘任务已压缩或复盘其他会话”分支下，当主代理认为有必要或当前项目治理要求独立评审时，才按第 1 节的委派方式交给未参与取证或形成建议的评审子代理（Start every subagent with a fresh context window (do not fork the current conversation).）。

委派独立评审时，在第 1 节的交接信息中补充用户纠正盘点、候选建议、证据定位、覆盖缺口、反证和关键推断。评审者按定位回查必要证据，不只复述取证摘要；实质修订后针对性复审。需要的核查未能完成时，说明缺口和实际核查状态，不声称已验证或适合直接实施；未做独立评审不等于没有做主代理核查。

报告中提及跨出 Skill 层的落点（无论是提出建议还是说明无需新增）时，**必须明确指明具体层级**（是“项目内文档/Spec（含已知路径或模块）”、是“项目/工作目录级 `AGENTS.md`”，还是“用户级全局 `AGENTS.md` / 个人全局提示词”），禁止使用笼统的“全局 `AGENTS.md`”混淆项目级与用户级；当项目文档层证据不足时，仅报告“项目文档/Spec 层待核实”并列明缺失项（体系存在性、收录门槛或目标位置），不伪造未证实的写入路径。

报告按以下顺序呈现：

1. **任务与证据概况：** 简要说明目标任务、实际使用的 skill（若未使用则明确写无）、证据覆盖及重要缺口。
2. **用户纠正逐次盘点：** 简要列出已覆盖区段内每一次用户纠正的定位、合理性核验与最终归宿（若本次任务无用户纠正，明确写无）：
   - **转入 Skill 层建议：** 合理且符合第 3 节第 1 层准入标准，明确标出子类（**已用 Skill 优化**、**已有未调用 Skill 补强** 或 **新建/拆分 Skill 提议**）并指向下方具体建议项；
   - **转入跨出 Skill 层的分流建议：** 合理且符合对应承载层准入标准，明确标出转入哪一层（**项目内文档/Spec**、**项目/工作目录级 `AGENTS.md`** 或 **用户级全局 `AGENTS.md` / 个人全局提示词**）并指向下方独立建议项；
   - **合理但无需新增通用规则：** 用 1–2 句话交代防复发评估结论（如已有明确规则覆盖仅属单次执行偏差、后续版本已修复，或经评估不满足上述任何适用层的准入条件）；
   - **不合理故不采纳：** 用 1–2 句话说明客观事实反证，解释为何当时情境下的纠正不宜固化；
   - **证据不足待核实：** 说明缺失证据及影响（含“项目文档/Spec 层待核实”或“与现有 Skill 重叠关系待核实”及其具体缺失项）。
3. **Skill 层建议（主责轨道，按实际影响排序）：** 按是否存在实质分支或边界代价取舍，显式分为以下两组呈现（仅输出非空组）：
   - **可直接采纳（单一明确方案）：** 仅限针对已有 Skill（含本次已用与已核实存在的未调用 Skill）且最小修改方向唯一、不改变核心意图或权限门禁、无明显副作用的建议。每项只给唯一方案，不硬凑备选，包含：问题或触发纠正的场景、可定位证据与实际影响；skill 归因（区分已用 skill 缺陷、当时已可用但漏触发、或仅作为当前优先承接载体）、防复发根因分析、反证及仍未确定的部分；最小修改位置与去特例化后的通用防复发修改方向；预期收益、成本、适用边界和评审状态。
   - **需讨论权衡（存在分支或代价取舍）：** 包含存在多个合理改法或边界取舍的已有 Skill 修改建议，以及**全部“新建或拆分 Skill 提议”**（因新建/拆分在复盘阶段仅是提议，具体边界与是否创建均需与用户讨论并获授权）。除归因、证据与影响外，须明确写出**待权衡的分歧点**，并以从 `1` 开始编号的列表呈现候选方向（推荐方案置为 `1` 并写明推荐理由与代价，其余备选写明适用条件与不作为首选的理由）。其中 **“新建或拆分 Skill 提议”只输出“新 Skill 概要卡片”**（不直接输出完整 `SKILL.md` 正文），卡片须包含：
     1. **建议名称与调用方式：** 用户手动触发（`disable-model-invocation: true`）还是模型按需触发，以及 `description` 触发边界草案；
     2. **触发依据与实际影响：** 本次会话中哪处任务痛点、返工或用户纠正证明需要它（附证据定位）；
     3. **核心职责边界：** 该新 Skill 包含哪些关键步骤/规则、明确不包含什么；
     4. **与现有体系的分工：** 与现有 Skill（若受可见范围限制无法完全排除重叠则注明“与现有 Skill 重叠关系待核实”）及 `AGENTS.md` 的边界切分；
     5. **建议来源与候选切分方案：** 从零新建还是从哪个已有 Skill 拆分，并以从 `1` 开始编号的候选列表给出待与用户讨论确认的立项/切分方案。
     **不得使用 `Q<N>` 标题或 `yjx-grill` 风格的独立问题块**，以免与实际调用 `yjx-grill` 混淆。
4. **跨出 Skill 层的分流建议（按需单列）：** 仅当存在超出 Skill 层职责但满足第 3 节第 2–4 层准入标准的建议时列出，同样显式按 **可直接采纳（单一明确方案）** 与 **需讨论权衡（存在分支或代价取舍）** 分组呈现（不使用 `Q<N>` 格式）；每项明确标出**目标层级与具体落点**（项目内已知文档/Spec 路径或模块、项目/工作目录级 `AGENTS.md`、或用户级全局 `AGENTS.md` / 个人全局提示词），并包含问题与证据定位、对应层机制归因、防复发修改方向（或候选权衡方向）、预期收益与成本。
5. **收尾决策分流提示：** 报告末尾简短汇总当前建议的决策状态（不自动调用 `yjx-grill`）：
   - 若仅有“可直接采纳”项：说明全部建议均为针对已有载体的单一明确方案，用户可直接确认实施；
   - 若包含“需讨论权衡”项（含“新建或拆分 Skill 提议”）：点明哪几项可直接确认实施、哪几项存在权衡分歧或属于新 Skill 立项提议（用户可直接按候选序号拍板并授权修改/创建，提出边界调整意见，或指定对应项调用 `/yjx-grill` 深入讨论后再实施）。

建议数量由证据决定，不设必须产出的条数。同一根因的多处问题或纠正可合并展开具体修改建议，但用户纠正盘点仍须逐次交代每处纠正的归宿；除用户纠正盘点与单列的分流建议外，其余未涉及用户纠正且被筛掉的琐碎内部试错仍不逐条列出。将“有证据支持的建议”“已检查范围内没有值得优化的问题”“证据不足无法判断”分开表达，它们可以分别适用于不同问题或区段。

完成复盘不等于授权实施，也不自动触发 `yjx-grill`。用户要求修改或授权新建/拆分 skill 时，保留证据、已确认边界和待核实事项再进入实施；提示文档采用静态审阅、一致性及包装/链接检查，脚本允许功能测试。不得创建、保留或运行模拟会话行为测试；静态检查通过不证明 prompt 行为可靠，实际收益通过后续真实使用观察。
