# yjx-retro-skill

由用户手动触发。主会话主持复盘，检查本次实际损失、用户每一次纠正行为，以及执行正确但可减少 Agent 参与的流程，寻找已有 skill 优化、新 skill 机会、协作文档与工程环境改进点。默认只调查并提出建议；修改文件、编写脚本、提交、部署、调度切换或操作外部系统属于另行授权的实施。

开始复盘时，先读取 `writing-for-agents` skill，将其作为评估与设计一切 Agent 消费文档（Skill、`AGENTS.md`、项目内文档及上下文指针）的统一标尺。

## 1. 确定证据范围与分工

默认复盘当前会话中已完成的实质任务（截止本次复盘调用前）；用户指定其他会话或任务时按指定范围。区分多个任务及其依赖，将复盘过程本身排除在被复盘任务之外。

主代理负责理解用户意图、安排调查、综合归因和交付建议。按被复盘任务的原始对话是否仍完整保留在当前上下文中分流：

- **当前上下文完整覆盖被复盘任务（未被压缩摘要替换）：** 直接以当前上下文中的用户消息、加载的 skill、工具调用与输出为主要证据，配合对相关 skill 文件、任务产物或 Git 状态的必要只读核验。全程由主代理单代理完成取证、归因、筛选与交付前核查；**不读取 [会话记录取证](references/session-evidence.md)，不查找或读取当前会话的磁盘原始记录（如 session JSONL），不启用取证子代理或独立评审子代理**。只要被复盘任务本身的原始对话仍在当前上下文中（即使更早的无关任务曾被压缩），即走本分支。若个别工具输出被截断或局部证据不足，直接记为证据缺口并限制结论范围，不回查磁盘日志或开启子代理。
- **被复盘任务在当前上下文中已被压缩摘要替换（含复盘前已替换或复盘期间被压缩），或用户指定复盘其他会话：** 当前上下文仍保留的原始消息与工具结果直接作为证据；对已被压缩摘要替换的区段或外部目标会话，读取 [会话记录取证](references/session-evidence.md) 定位磁盘原始会话记录并固定截止点（压缩摘要仅作定位线索）。将补读磁盘原始记录的只读工作交给上下文隔离（`fork_turns: "none"` 或平台等价机制）的子代理（Start every subagent with a fresh context window (do not fork the current conversation).），传入本 skill、目标记录定位、用户目标与约束、明确调查范围及返回要求；子代理分段读取并仅返回带定位的精简证据包，主代理按定位回查关键原文。若宿主无法使用子代理，主代理说明限制并自行分段读取必要区段。

按时间线建立覆盖记录，再围绕疑点检索：覆盖用户要求、**用户的每一次纠正行为**（显式纠偏、推翻或修正 Agent 输出与做法、中途叫停不当动作；普通方向切换先核实是否属于对偏差的纠正）、实际加载的 skill（未使用则记为无，并在已知可用列表与目标仓库相关范围内识别可承接职责的候选 skill）、关键工具结果、失败与返工、最终交付及核验。当前上下文分支使用消息顺序或事件定位；磁盘取证分支使用记录路径与行号或稳定消息 ID。记录已覆盖区段与缺失、截断或仅有摘要的区段。

完成条件：定位被复盘任务、实际使用的 skill（或确认未使用）、已覆盖区段内的全部用户纠正行为和证据范围，无法还原处标为缺口。综合整个会话检查 Skill 与工程改进机会，按第 3 节分流。

## 2. 逐次复盘用户纠正与实质问题归因

结合错误、误解、返工、高昂工具调用成本、信息获取障碍与交付缺口寻找候选问题，并对已覆盖区段内**用户的每一次纠正行为**逐一复盘。必要时只读核验相关产物、来源、脚本或外部状态（不附带写入或重跑日志中的动作）。对会话中耗时较长或反复拉锯的调查与对齐环节，先结合用户角色与职责边界判断该环节本身是否属于越界冗余投入；若属越界投入，应提炼“划出职责边界、不做深入处理”的减法规则，避免把越界探查动作反推为正向必做步骤。

**确定性流程与工具经济性：** 主动检查重复或周期执行、按固定规则转换或比较数据、大量原始输出进入模型上下文，以及模型仅负责启动已有命令的流程；即使没有错误或用户纠正，也评估能否由脚本、CLI 或调度承担正常执行，只在需要判断的节点调用模型。用户主动提出脚本化、自动化或降低调用成本时，同时追问该机会为何未被 Agent 提前识别，不因它属于需求变更而跳过。保留实际调用、数据流和频率的证据，按第 3 节评估收益与落点。

评估用户纠正时，将“纠正是否合理”与“是否固化为通用规则”解耦（**并非每一次纠正都客观正确，但大概率符合用户偏好**）：

- **合理（指出真实偏差或符合用户偏好/当次合理意图）：** 指出了执行偏差、理解错位、低效默认行为、过严/缺失门禁，或表达了跨场景协作偏好。所有合理纠正均须追问“当时为何走到需要纠正这一步，后续如何从机制上防复发”。
- **不合理（受当时信息偏差或事实误判影响）：** 经客观事实与上下文核验，因当时信息不完整或误判状态给出，按其修改会导致错误或退化。
- **证据不足无法判断：** 因上下文截断或外部状态不可考无法核实，保留为待核实缺口。

对每个候选问题及每次合理纠正，核实事件过程、偏离的目标或稳定偏好、实际影响、当时适用或可承接职责的候选 skill 边界（尽可能核实执行时版本与可用状态），按以下类别归因（可记录共同原因）：

| 原因 | 处理 |
| --- | --- |
| 本次已使用 Skill 缺口、冲突、默认行为违背高频偏好或过严 | 分析防复发机制，按第 3 节第 1 层评估最小通用修改 |
| 已有但本次未调用 Skill 的触发或内容缺口 | 只读核验候选 `SKILL.md` 正文、职责边界及其引用的下游依赖（关联 Skill、脚本或命令入口）：若候选 Skill 的核心依赖已缺失断链或已被当前实际工作流取代，提议清理或归档该陈旧 Skill，不向其同步新规则；若仍然有效，证实任务执行时已可用且允许调用的归因为触发指针（`description`）/入口导航缺口或执行漏调，仅确认当前存在而无法证实当时可用的作为**当前优先复用承接的已有 Skill 优化目标**，不倒推为历史漏调 |
| 可复用按需工作流缺失或现有 Skill 职责过载 | 具备跨任务复用价值、仅特定场景按需触发（不宜常驻 `AGENTS.md`），且经核验现有相关 skill 正文无匹配项（或塞入会导致职责过载）时，转入第 3 节“新建或拆分 Skill 提议” |
| 项目内文档 / Spec / 知识库缺口 | 属当前项目的运行时机制事实、架构决策或特定模块非显然边界的，按第 3 节第 2 层核验体系存在性与收录门槛后决定去向 |
| 项目/工作目录级或用户级全局协作层缺口 | 属仓库/目录级持续约束或跨项目个人通用偏好的，按第 3 节第 3、4 层分流 |
| 确定性流程仍依赖模型逐次执行 | 按第 3 节工程改进路径评估自动化与模型保留边界；不以发生错误为前提 |
| 工具成本过高、信息可观测性不足或代码工程门禁缺失 | 当会话因昂贵工具调用、缺少日志/状态只读入口绕弯，或业务代码出现了本可由代码 Linter/CI/脚本拦截的机械错误时，评估补充只读辅助工具或代码工程检查；工具/环境客观限制则指出能力边界（仅在 skill 降级流程有问题时修改 skill） |
| agent 未遵守已有明确规则 | 记录执行偏差；仅当证据显示规则难以发现、表述冲突或违反 `writing-for-agents` 准则导致失效时才建议重构规则，否则作为“合理但无需新增通用规则”结案 |
| 单次任务特例 | 单次事故口径、当次临时改主意或随本次修复即失效的问题，直接排除在任何规则、Skill 与文档修改之外 |
| 原因未知或证据不足 | 列明缺失证据及对判断的影响，保留为待核实 |

对照已有保护措施和反证，已在后续版本解决的问题不再重复建议修改。

## 3. 筛选最小优化与落点分流

正式建议须同时具备具体证据、实质影响（或合理纠偏信号）、机制归因，以及在目标承载层内的持续复用价值（一次严重问题或一次合理纠正即可触发）。所有建议必须**剥离单次事故表象、具体报错值、当次对话原话及一次性 Bug**，并遵循 `writing-for-agents` 准则（精准触发指针、单一事实源、正向指令、剔除默认已遵守的 No-op）。

在落入文档前先做**机械 vs 判断分流**：针对业务代码或外部副作用逻辑的固定语法/命令/约束问题，优先通过项目既有代码 Linter、构建检查或可复用脚本拦截，把文档留给需要语境权衡的判断型准则；**严禁为 Markdown、Prompt、Skill、`AGENTS.md` 等文本型文件创建对应的测试文件或机械检查脚本**。

**脚本、CLI、调度与工程环境建议**独立于下述文档四层：先核对已有实现与接入方式，再比较预计复用次数、模型调用与上下文开销、开发维护成本及仍需模型判断的边界。收益不足时保留现状；成本数据不足时标明推断，不编造 Token 节省量。任务专用编排落在任务项目；通用能力按目标仓库规则复用或抽取。涉及发送、更新等外部副作用时，说明授权、幂等、回执与失败恢复要求；部署或调度切换列为另行授权的步骤。工程建议直接给出实现归属、已有入口或待核实位置，无须包装成新 Skill 或文档修改。

文档类建议按作用域、信息性质与上下文常驻成本（优先落入按需加载层，减少每轮常驻负载），在以下四层中精确定位并遵守各自的准入与命名规则（后续报告提及不改 Skill 而改项目文档或 `AGENTS.md` 的建议时，**必须直接写明下述第 2–4 层的完整名称与目标文件路径**，不得使用笼统的“全局 `AGENTS.md`”混淆项目级与用户级）：

1. **Skill 层建议（按需加载）：**
   - **已用 Skill 优化 / 已有未调用 Skill 补强：** 适用于本次已用 skill，或在已知可用列表与目标仓库相关范围内只读核验 `SKILL.md` 正文后确认可承接职责的已有未调用 skill（修改工作流步骤、`description` 触发指针、检查点、分流路由或降级规则）。改动须在该 skill 覆盖范围内跨模块、跨工单通用。提议修改前先核实目标 skill 的维护归属：第三方外部开源 skill 不直接原地修改，确需定制时提议在用户或项目自有技能仓派生独立 skill，并同步扫描更新 `AGENTS.md` 与关联 skill 中的旧名称引用（扫描 `~/.codex` 等宿主目录时精确指定配置文件或显式排除 `sessions/`、`log/`、`visualizations/` 等运行时大目录）。
   - **新建独立 Skill 或从已有 Skill 拆分提议：** 须同时满足：（a）有跨任务重复触发信号与实质减负价值；（b）属特定场景按需加载的多步流程或专项规程，不宜常驻 `AGENTS.md`；（c）已只读核验相关候选 `SKILL.md` 正文确认无职责匹配项，或现有 skill 需按调用时机/序列边界拆分（若受可见范围限制无法完全排除外部重叠，标注“与现有 Skill 重叠关系待核实”）。按 `writing-for-agents` 判定调用方式：领域知识、规范参考与表达风格类 skill 默认设为模型可自行调用（不设 `disable-model-invocation: true`），仅需用户显式点名启动的阶段编排或高副作用入口工作流才设为手动触发。复盘阶段**仅输出“新 Skill 概要卡片”提议**，不直接生成完整 `SKILL.md` 正文。
2. **项目内文档 / Spec / 知识库建议（不改 Skill，按阶段/模块加载）：**
   - 仅当已有上下文、项目 `AGENTS.md` 或已加载 skill **已证实该项目维护了对应文档体系**时启用（严禁假设项目必有 Spec/知识库或凭空要求新建该体系）。内容须属跨任务复用的运行时机制、架构决策或业务模块非显然边界，剥离单次事故流水并符合该项目自身的收录标准。分流至项目内文档时，先核实该事实的适用范围是单模块私有还是跨模块/全项目通用，按实际适用半径落入对应层级，避免将跨模块通用事实埋入单模块文档（范围不明时保留待核实）。若项目无此体系或未达门槛，直接排除本层并继续评估其余层；若当前证据无法确认体系存在性、收录门槛或目标路径，记为“项目文档/Spec 层待核实（列明缺失项）”且不盲目全仓扫描。
3. **项目/工作目录级 `AGENTS.md` 建议（不改 Skill，当前仓库/目录常驻）：**
   - 适用于当前仓库或工作目录（含子目录 `AGENTS.md`）内需持续遵守的协作约束、仓库拓扑、编译测试边界、提交规范或顶层导航指针。允许保留落实约束所必需的仓库或目录身份。
4. **用户级全局 `AGENTS.md` / 个人全局提示词建议（不改 Skill，所有项目常驻）：**
   - 适用于跨所有项目复用的个人沟通偏好、问答格式、工具优先级、子代理协作策略等通用规则（如 `~/.codex/AGENTS.md`）。必须彻底剥离具体项目、仓库与业务特征。

优先选择最小改动：能通过澄清现有 skill 适用条件、锐化触发指针、调整默认动作、消除重复或删减过严约束解决的，不新建 skill。区分“无实质收益的字眼/目录挑剔”与“能稳定减少协作摩擦的用户偏好”，仅将后者去特例化后纳入建议。预期收益作为推断表述，缺失证据保留为待核实线索。

## 4. 核查与交付

交付前，主代理对照第 3 节标准核查每项候选建议的证据、合理性、归因、去特例化程度、职责边界及修改影响，剔除绑定单次事故特征或未达目标层准入标准的候选。当前上下文完整分支由主代理直接完成核查；仅在“被复盘任务已压缩或复盘其他会话”分支下，当主代理认为有必要或项目治理要求独立评审时，按第 1 节方式派发给未参与取证或形成建议的上下文隔离评审子代理（Start every subagent with a fresh context window (do not fork the current conversation).），传入用户纠正盘点、候选建议、证据定位、覆盖缺口与反证，由评审者回查必要原文并在实质修订后针对性复审。核查未完成时如实说明缺口。

### Agent 核查与用户交付分离

第 1–3 节要求的逐次纠正盘点、证据对照、归因、候选筛选与处理去向由 Agent 在分析过程中完整核查，用于形成可靠结论，不作为默认逐项展示给用户的审计清单。这里的内部核查是 Agent 的分析职责，不要求另建审计文档，也不代表已经保存了持久记录；确需持久化时，明确记录的用途、位置与授权范围。

内部核查仍须覆盖所有用户纠正、各候选的证据与反证、维护归属、落点层级、影响和代价、适用边界及评审状态。区分已解决、无需新增规则、不采纳与证据不足等去向，不能因对外交付精简而省略调查或漏掉有效问题。对外结论涉及的关键依据、风险、未决事项和影响判断的证据缺口，随该结论一起交付。

### 面向理解、决策与行动交付

首句直接给出本次最重要的结论或建议，再按实际问题和影响排序，先呈现最有价值的少量事项。每项提供足以让用户理解和判断的背景、关键依据、具体改法与落点、实际影响和代价，以及确实需要用户决定的部分；不要把“简短”变成省略判断背景。实际使用的 Skill 名称简要列明，证据范围或缺口仅在影响结论可信度时展开。

按当前问题组织结果，不按内部核查字段或文档分类依次汇报。同根因的纠正可综合成一项结论，已解决的问题只在影响当前判断时简述；其余细节保留在 Agent 核查中，按用户追问或后续议题需要逐步展开。信息筛选不设会截断关键风险或有效问题的硬条数上限。用户要求全面展开时，再围绕其用途提供完整结果，不默认倾倒核查清单。

建议按第 3 节落点规则写明目标 Skill、文档层级与具体文件路径。新建或拆分 Skill 时，仅在用户需要判断立项时提供概要卡片，包含名称与调用方式、触发依据、职责边界、与现有体系分工、来源与候选切分方案，不生成完整 `SKILL.md`。脚本或工程建议说明自动化与模型判断的边界；有外部副作用时交代授权、幂等、回执和恢复条件。

### 决策与下一步

只有针对已有 Skill、最小改法唯一且不改变核心意图或权限门禁、无明显副作用的建议，才列为可直接确认实施。存在分支、代价取舍或新建/拆分 Skill 的建议，说明真正待定的选择，再用从 `1` 开始的数字选项呈现：推荐项说明理由与代价，其余说明适用条件与不首选理由。不使用 `Q<N>` 标题或 `yjx-grill` 提问块，不为每个核查条目制造选择。

结尾说明当前结果与实际下一步。需要用户判断时，只提出当前可决定的事项；没有用户待决事项时，不虚构确认题，也不把 Agent 权限内能完成的工作交给用户。用户可直接授权单一明确方案，或选择候选方向、调整边界、另行调用 `yjx-grill` 深入讨论；本 Skill 不自动启动对齐流程。无值得修改的问题时，给出有边界的简短结论，不强行产出建议。

完成复盘不等于授权实施。获用户授权修改或创建文档/Skill 时，保留证据与已确认边界，按 `writing-for-agents` 准则实施，并通过静态审阅、一致性及包装/链接检查验证；仅对具备不可逆/外部可见副作用或失败难以手工察觉的核心代码允许功能测试，**不得为 Markdown、Prompt、Skill、AGENTS.md 等文本型文件创建、保留或运行模拟会话行为测试或任何对应的测试文件**。
