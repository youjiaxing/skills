# 发现问题与按需取证

当目标仍含糊、补救方案缺少问题依据、需要核验既有机制、判断依赖表现，或用户指定了正式结论载体时，读取对应主题。证据已经足够的常规讨论不额外执行本文件的全部分支。

## 从补救方案回到实际问题

区分用户观察到的困难、对原因的解释和提出的补救方案。只有具体方案却缺少目标依据时，先结合现状提出可纠正的理解，再比较能满足同一结果的更轻方案；这项前提先于原方案内部细节。若按需求措辞实现会改变共用机制，先用一组真实配置、操作和预期结果核对业务目的，再比较沿用现有机制是否已足够；推荐变更前说明现有机制的不足、受影响调用方和沿用现状的备选。已有场景依据充分时直接复用，不增加固定问卷。

默认自然表达可能是近似词或直觉比喻，把它当作调查起点，不当作不可调整的边界，也不否定用户已明确声明的目标。

- **方向已有，只缺准确概念**：结合真实系统帮助命名并深化，不扩大范围。按需要关注专业实践中的隐性关键步骤、一手素材、具体方法/工具和客观验证信号；它们是调查视角，不是每次必问的四项问卷。专业推断仍是推断。
- **目标尚未成形**：问最近的实例、原本想完成什么及实际阻碍，用方向有差异的具象对照帮助取舍；不要用精深术语和完整专家方案锁死方向。选项会过早限制答案时用开放问题。需要制作可感知材料时走下文的表现前提。

诊断对既有产物的不满时，区分缺失的呈现/消费层和既有结构的功能价值。先检验保留筛选、批量浏览、状态维护等有效结构，再补齐导读或总览，是否足以解决问题。

只有目标不匹配、重大无依据假设、不可行性或更小范围有明确收益时才挑战方案；少做或不做可以是答案，但不另加固定“为什么”访谈。借外部案例提炼规则时，剥离原案例表面的身份或固定口令，检查背后是否是更普遍的常态。

## 核验实际机制

按会改变当前选择的事实取证，不做无关全库调查，也不把 Agent 可查明的事实转问用户。

- 核查既有行为时从实际入口、当前配置与命中分支追踪，不用死分支证明现状。局部封装没暴露某能力时下探底层组件，不把封装缺口当成底层不支持。
- 涉及定时调度或宿主资源时，先查实际托管方式、电源/休眠与运行形态；管理、调试接口的能力方向也先查源码，不凭空构造逆向或任意回退场景。
- 候选方案依赖某产物的维护职责或资源规模时，先核对实际生成/更新链路和资源集合，再谈取舍。
- 分析缺陷时恢复参与者动作、可观察失败和最小因果链，区分已证实原因与假设，说明已排除的伪原因。
- 涉及性能时先核算触发规模、时间集中度、并发与持久化 I/O 总成本；单次轻量不等于总体便宜。只有证据显示最小满足方案成本过高时，才讨论降级，不默认裁剪需求。
- 讨论失败、并发或重试风险前，查清宿主及中间件已有事务、原子回滚、重试和去重保证。默认能力已覆盖或缺陷未经证实时，不制造额外风险问题；需要补救时先比较现有低成本路径。

常规机制、实现细节或已明确委托事项可由 Agent 推导；权限、保证和整体策略的重大变化仍回到问题门禁。执行主体具有权限内修复能力时，优先考虑先自愈、失败或需人工介入再告警，而不是默认只报警。已委托的自动化应保留，触发条件脆弱时优先替换成可验证结构特征。

已有工作基线或实现中途的局部对齐，不重新盘问在途改动去留。只有未确认归属且与本次目标冲突的改动，才先区分稳定行为、当前改动和目标，再对齐保留修补或舍弃重做。前者答案会改变后续细节是否成立时，先解决它。

## 作用域与工作顺序

新增可复用工具或流程前，查清使用者、运行范围和分发边界，再选承载方式；事实能决定的不用问。按既有组织维度安排目录通常由 Agent 决定。用户质疑现有组织维度且影响演进时，先讨论沿用或调整结构，不在送审前自行锁定。

## 新 Skill 或工作流的最小行为样例

当方案包含新建或重大整合 Skill、自动化工作流或用户可见的 Agent 能力时，在最终批准前给出一个最小具体样例，至少说明：什么输入或任务会触发、Agent 会执行什么关键动作、用户会看到什么结果，以及明确不处理什么。样例使用真实或已脱敏的代表性场景，不把完整实现伪装成样例，也不要求先创建正式文件。

如果用户表示还不了解该能力、无法判断效果或看不懂方案，暂停批准请求，先补充这个样例；用户理解后再继续方案批准。样例用于判断预期行为，不授予实施权限，也不替代必要的正式评审、原型或执行授权。

只把会改变当前方案可行性或选项的调查作为前置阻塞；共享背景或模块归属的独立核查可并行或后置。调查尚未返回时，其依赖问题不能先问。两个问题即使都必要，只要答案会改变对方的背景或选项，就不是正交问题。

## 表现前提

当选择依赖视觉层次、信息密度、交互，或视频/动画/音频等高成本创作的实际效果时，先用低成本、可感知的材料验证：

- UI 与交互使用已安装的 `yjx-prototype`。
- 高成本非 UI 创作使用分镜、动态草图或代表性样段。

任务已包含对应制作授权，且不触发未授权的外部写入或付费生成时，直接制作验证；否则先建议，不能仅凭抽象描述请求全量生产。用户确认后把表现和关键边界合入结论，再进行适用的独立评审与实施批准；用户明确选择其他处理方式时保留其真实范围。

用户自行体验不意味着模型必须读图。模型需要观察时，简单、一次检查可直接读；持续视觉上下文值得隔离，或用户明确要求时，按注册名发现并使用 `yjx-image-reading`，缺依赖则报告。沿用它的输入准备和只读观察，不重复实现压图或切片。来源、操作授权、证据覆盖与未决状态始终由当前流程保留，不能为省成本减少必要画面。

## 用户指定的结论载体

用户指定语雀设计/接口文档、`.proto` 等作为结论载体时，生成与更新属于当前切片交付；不必因此进入业务实施。若要求先交付外部契约而字段尚未定稿，先在讨论中完整盘点清单、字段和编号，确认后按目标项目标准路径落地。

不夹带业务代码、未要求的归档或打包产物。宿主 File Watcher 正常刷新的对应生成物属于伴随产物，不算越界业务实现。

当前结论已落入指定载体后，后续讨论修订、推翻或补充它时，同步更新原载体再进入下一切片。外部文档引用代码枚举/常量作为真源时，先确认并落实代码定义，再更新引用文档。持久化结论不等于授权实施其他部分。
