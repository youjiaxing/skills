# 项目内模块与进度

## 从讨论进入跟踪

按需求里的独立交付范围识别模块，不按文档长度、文件数量或一次会话能否完成来拆分。讨论阶段即可先列模块、相互依赖、已知进度与待确认边界，阶段结论变化时修订同一份记录。只分析一个问题不自动建项目；单点工作沿用总清单一行即可。

本路径直接接受需求文档、现有项目页、讨论结论和用户反馈；不依赖特定的讨论或拆票 Skill。跟踪记录不是实施票，也不据此启动开发、提交、发布或通知他人。

先从用户指定链接或总清单中的原需求定位唯一项目页，读取内容、子库 schema、视图与相关记录。一个大需求在个人总清单保留一行，模块和待办留在该行的项目页内部；不创建跨项目子待办总库。已有页面按实际 ID 复用，不凭同名另建。

只有目标和写入范围已明确授权才落盘。已授权的同一项目按阶段结论及重要事实持续更新，无需每次重新申请；不把已绑定 ID 或对某个建议的认可当成新建项目、改 schema 或扩大范围的授权。尚无授权时先交付草案；目标有歧义时只澄清该缺口。

## 页面与表

首次创建前读取[项目模板](../templates/project.md)，按需求裁剪；既有项目优先保留其有效结构，仅在已有授权内调整。

- **项目总页**：需求出处、范围摘要、当前整体结论与主要阻塞；顶部用“关键里程碑”表，按计划日期排序，同一天可合并。日期只是计划，不代表工作已完成。年度/日期未知则明确未知，不编造承诺。
- **模块进度表**：一行一个可分别推进或验收的业务模块。主要视图优先显示模块、开发阶段、当前进展/剩余工作和下一步；避免把编号等辅助字段挤在最前。子功能留在该模块页，除非确实具有独立的交付责任。
- **模块详情**：范围与复用边界、`子功能｜实际进度｜剩余工作 / 验收依据`、已确认决定/待确认项及需求/证据链接。正文和属性更新保持一致，记录核实时间，旧结论过期时局部修订而不堆叠互相冲突的“最新结论”。
- **开发待办**：只记录影响交付、需要独立安排或持续协调的重要事项，关联受影响模块并写清前置条件。某个模块的阻塞优先记在该模块；仅有独立跟踪价值时另建待办，避免与模块页重复维护状态。负责人和期限有依据才填。

模块按业务范围组织，里程碑按交付结果组织；一个里程碑可以涉及多个模块。活动编号、英文标识、设计文档、后台接口、数值配置核对等是领域可选字段，按项目实际需要设置；不把某次活动的字段全量复制成通用必填项。

普通代码步骤、生成 JSON、改字段、补配置、跑编译都不单独建待办。记录对交付有意义的结果或尚未解除的阻塞，不把项目页变成工具执行日志。

## 开发阶段与证据

以下为开发项目的默认模板，采用前先核对项目约定。已有 schema 不一致时先说明映射/差异，不自动删状态或迁移旧记录。

| 分组 | 状态 |
| --- | --- |
| 待办 | 未开始 |
| 进行中 | 需求分析中、开发中、开发中（阻塞）、等待自测、等待联调 |
| 完成类 | 完成、无需开发、无需开发（已交接） |

正常推进：`未开始 → 需求分析中 → 开发中 → 等待自测 → 等待联调 → 完成`。开发阶段遇到阻塞时用“开发中（阻塞）”，解除后按实际工作恢复。需求判断不需要开发则“未开始 → 无需开发”；已经进入分析后才确认无需开发，也按事实结束，不伪造未发生的阶段。任务交接可从任意阶段进入“无需开发（已交接）”，表示个人责任结束，不表示接手人已完成开发。

不另设“挂起”“开发完成”“自测通过”。后两者是转换条件：

- 模块已约定开发范围全部完成，才进入“等待自测”。
- 适用的自测通过，才进入“等待联调”；编译、提交、静态检查成功不能替代自测。
- “完成”按该模块已约定交付和验收依据判断，不自行增加或取消验收门槛。
- 只有部分子功能得到验证时更新该部分，不把局部结果提升成模块整体完成。不存在的阶段不伪造经过记录；证据缺失时保留阶段并记录缺口。

依据可以是用户明确的进展反馈或覆盖目标范围的实际验证结果，记录来源与核实日期。有充分依据可直接更新阶段；推断、未来计划和待确认方案须保留其性质。与人工结论冲突时先列出差异，不覆盖人工结论或武断推进。自测失败、需求变化等需要回退时按已核实的剩余工作记录，不只允许单向前进，也不按日期自动推进。

“人工核对结论”等人工字段，只有用户明确点名才改；Agent 在自己维护的进展/核实结论中记录新证据。项目阶段变更不自动改总清单的个人状态、顺序或 TB。

## 落盘与告知

实际写入前使用[项目写入协议](project-operations.md)。schema、属性与正文是不同对象：属性按完整可写快照保护，正文按授权区段精确编辑；未经授权不整页替换、不清空人工补充、不删除已有子库。

重要结论形成、阶段转换、阻塞解除或交接时更新；不逐轮抄聊天、无变化不重写。每次写入并完成核对后明确告知用户对象、前后变化与依据，可把同批结果合并说明并附页面链接。结果未知或部分失败时报告具体范围及恢复动作，不把已派发当成功。

公开参考仅用于理解选择，不是强制依赖：

- [Thomas Frank 的 Tasks 数据库说明](https://thomasjfrank.com/docs/ultimate-tasks/databases/tasks/)：用关联和视图复用记录，避免重复维护。此处不据此把项目内部待办汇总进个人总清单。
- [KoRo 的项目工作流](https://www.notion.com/blog/notion-koro)：重复结构用模板，具体工作按项目确定。
