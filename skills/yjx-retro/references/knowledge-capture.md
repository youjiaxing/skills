# 知识筛选与沉淀

在已覆盖会话中发现值得留下的认识时加载本参考。知识筛选独立于过程改进；无报错、无纠正或无整改建议的区段同样需要检查。

## 判断是否值得留下

围绕未来会用到的判断或动作寻找候选：解释机制的原理、已验证的有效方法、成功或零收益实验的适用边界、选型与排除理由、用户正向认可、实际能力与限制。对每项说明：

- **认识**：得到了什么可复用认识，或需要保留的项目事实/案例。
- **证据**：稳定原文定位、实际工具结果或产物；分别标明用户确认、工具实测、助手推断。助手说“可行”不等于能力实测。
- **条件与限制**：适用对象、环境/版本、样本与未验证范围；结论强度不超过证据。
- **未来用途**：什么条件下读取它，能帮助哪项判断或避免什么重复探索。

一次可靠核验即可支持有边界的知识，不要求跨会话重复；一次用户认可只保存具体案例，不能直接升级成长期偏好。成功运行仅支持实际观察到的能力，不能扩为所有环境都可用；认可某种方案不授予永久调用权限。没有新认识、没有未来用途或无法核实的断言不作确定知识沉淀；仍有价值的假设可在建议中标为待核实。

## 先查真源再提落点

从已知项目入口、当前任务产物及实际使用的 Skill 定点查找，不为知识候选遍历所有仓库或新建知识体系。逐项判定：

| 当前状态 | 处理 |
| --- | --- |
| 已有正文与边界，且可发现 | 复用已有位置，不重复写正文 |
| 正文充分，但相关入口难发现 | 建议在实际触发点补有读取条件的指针 |
| 正文或适用边界缺失 | 在已有真源补最小增量，保留依据 |
| 尚未确认所属体系或没有合适载体 | 交付候选与落点问题；不擅自新建知识库 |

通用方法优先归已有 Skill，项目事实和决定归项目文档，单次选择/认可归已有专题案例。只有确需改变执行规则时才进入过程改进筛选，不能把全部知识改写成常驻提示词。涉及公开 Skill 时剥离私有身份、渠道、价格、密钥和项目细节，必要时只在私有真源保存。

## 交付与授权

仅报告有实际增量的知识或发现性改进，并给出拟存位置与具体增量；保存充分的条目内部复用即可。默认只建议，已获本次写入授权才落盘并核验链接、正文与边界。`retro-ledger` 保持改进候选/决策职责；知识正文不进台账，同源已拒绝建议也不能改名后重新推销。
