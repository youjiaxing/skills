# Maintenance: yjx-implement

本文档记录了 `yjx-implement` 的架构考量、与原版 `mattpocock/skills` 的缺陷演化对照，以及防漂移规则。在评审、修改或重构本 Skill 时必须先行查阅。

## 1. 设计初衷与演进历史 (Design Rationale & History)

`yjx-implement` 旨在彻底替代 Matt Pocock 原版极其单薄的 5 行 `/implement` 指令，将其重构为兼具**骨灰级架构师审美**与**工业级交付纪律**的手术刀式代码实施引擎。

原版 `/implement` 仅是一段简单的提示词拼接（“按 spec 实现”、“用 /tdd”、“最后跑全量测试”、“用 /code-review 审查”、“允许就 commit”），在真实工程场景中会高频引发：范围失控漫游、绿灯篡改作弊、全量测试卡死、滥用 Mock 摧毁可读性、以及污染 Git 分支等致命问题。

---

## 2. 解决的核心工程痛点 (Pain Points & Mitigations)

### 1. 资产绕行与自作聪明造轮子 (The Asset Bypass & NIH Trap)
* **痛点**：若盲目强调“第一性原理与原生实现”，Agent 会绕过项目团队经过长期沉淀的基础库（例如：Go 项目已封装统一带时区和测试时钟的 `pkg/time`，但 Agent 却强行使用原生 `time` 包；或绕过统一的 `pkg/errors`、统一日志、上下文链路）。
* **对策**：确立**资产复用阶梯**：`项目既有统一封装 (最高)` > `语言标准库` > `引入新外部依赖`。要求编码前优先检索复用既有组件，严禁私自另起炉灶。

### 2. 绿灯造假与断言篡改 (Green Laundering & Assertion Tampering)
* **痛点**：Agent 在实现复杂逻辑遇到测试报错时，极易发生道德滑坡——通过改小期望值、删除测试用例或注释掉断言来强行“凑绿灯”。
* **对策**：建立**零断言篡改红线**。公式化定义：严禁私自删改已有断言，仅当对齐方案中显式声明了对应行为的契约变更时，方可合法调整对应测试。

### 3. 为测而测摧毁可读性 (Over-Testing & Readability Destruction)
* **痛点**：模型常把“可测试性”等同于“每个内部类都必须抽取 Interface、每个依赖都必须通过 DI 注入、每个分支都必须 Mock”，导致简单业务被拆成千层饼，代码直观可读性彻底毁灭。
* **对策**：明确确立**“可读性高于可测试性”**信条。严禁为了单元测试强行捏造假接口与多态包装，核心业务必须因果最短、直来直往。

### 4. 全量测试超时灾难与体量自适应 (Full Suite Timeout & Scale-Adaptive Testing)
* **痛点**：原版要求“最后跑 full test suite”，在中大型工程中动辄耗时十几分钟甚至直接卡死；但若一刀切死锁测试，又让几秒钟就能跑完的小微项目丧失全局验证的便利。
* **对策**：确立**体量自适应验证**。小微项目允许秒级跑通全量套件；中大型工程/多仓工作区严格禁止在各级根目录盲目执行递归大测试（如 `go test ./...`），测试严格物理收敛在叶子单文件/函数级别，非必要不测。

### 5. 外层容器陷阱与非阻塞预检 (Workspace Container Trap & Lightweight Pre-flight)
* **痛点**：根目录常常只是一个不含业务代码的工作区外壳容器，盲目在根目录跑测试或查 Git 会误伤；且若在 Phase 1 强行要求跑基线测试，会喧宾夺主打乱主线编码节奏。
* **对策**：以被修改文件为锚点**就近溯源工程与 Git 边界**；Phase 1 保持为**纯轻量的上下文锁定**，轻量探针仅为可选辅助，绝不主动强跑测试阻塞主线。

### 6. 命令挂死与交互式陷阱 (Hanging Interactive Watchers)
* **痛点**：自动执行 `npm test` 或 `pytest` 时，测试框架默认进入 watch 模式等待交互输入，导致 Agent 进程无限悬挂。
* **对策**：命令嗅探阶段强制追加非交互/CI 标志（如 `CI=true`, `--watch=false`）。

### 7. 意图锚点与废话注释防注水 (Why-Anchored Positive Prompting)
* **痛点**：简单否定“不要写废话注释”易触发 LLM 负面诱导效应（要么完全不写注释，要么写出更多无用注释）。
* **对策**：采用正向引导词 **Why-Anchored Comments**：代码通过结构和命名自解释 WHAT 和 HOW，注释仅且只保留 WHY（非直观业务约束、极端边界绊线与被放弃方案的权衡）。

### 8. 项目治理优先与通用工单挂接 (Governance First & Universal Tracker)
* **痛点**：原版假设任意分支皆可 commit，且硬编码对 GitHub `#123` 的偏见，在企业级分支保护和多工单系统（Jira, Teambition 等）下直接翻车。
* **对策**：在保护分支或必须 Code Review 时严禁自动提交；在允许提交时执行 Conventional Commit，并自适应提取附带任意格式的工单标识（如 `PROJ-123`、`TASK-88`）。

## 3. 防漂移验证清单 (Anti-Drift Validation Checklist)

在修改或维护本技能时，检查是否发生以下退化：

- [ ] **资产复用阶梯未退化**：是否依然强制要求优先复用项目既有的公共封装（如 `pkg/time`），而不是无脑裸写标准库或第三方库？
- [ ] **反膨胀守则未破坏**：`SKILL.md` 正文是否依然严格控制在 100 行以内的高密度纯执行模式？
- [ ] **体量自适应未被教条化**：是否允许小微项目秒级跑全量，同时严禁大型工程盲目跑漫长的递归大套件？
- [ ] **外层容器与子仓边界清晰**：是否以被修改文件为锚点就近判定有效工程和 Git 仓库？
- [ ] **预检保持非阻塞**：Phase 1 是否未强加任何测试步骤，保证主线顺畅？
- [ ] **反绿灯造假门禁健在**：是否依然严禁未经批准的已有测试断言弱化或删除？
- [ ] **可读性红线坚固**：是否依然明令禁止为 Mock 强造假接口的过度设计？
- [ ] **治理门禁完备**：是否在需要 Code Review 或保护分支时绝对禁止越权提交？
- [ ] **通用工单挂接兼容**：commit 规则是否兼容非 GitHub 类的多种工单标识？
