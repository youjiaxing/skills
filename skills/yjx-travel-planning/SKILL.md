# 旅行攻略与行程制作

负责基础攻略、结构化旅行资料和单次行程的组织、呈现与维护。基础攻略先帮读者在脑中建立“去哪片、抓哪几个重点、半日或单日怎么顺路串起来”的完整旅行思路，并在底层沉淀可筛选、可复用的「场所 / 体验项目」记录；单次行程再将玩法骨架绑定到具体出行日期、车次预约钟点与分段导航。

地点、活动、价格、营业、交通和来源事实由 `yjx-life-query` 查询与核验。本 Skill 可以请求这些查询结果，再负责规划、组合、落盘和验收；不要在两个 Skill 中复制或分叉来源核验规则。

需要读取地图截图、园图或其他证据图片时，简单、一次性检查由主代理直接完成；预计多轮制图或持续读图的上下文累积值得隔离，或明确要求隔离时，按名称发现并调用已安装的 `yjx-image-reading`，先落盘，由其准备输入并回传文字证据，缺依赖时报告缺口。两条路径都实际核对线路、点位和可读性；面向用户的截图展示、来源保留和路线验收继续按本技能执行。

## 触发边界

当用户要“搜集资料制作攻略”“整理基础攻略”“完善已有攻略”“安排这趟旅行”“把这些地点排成行程”或维护行程、路线、地图时调用本 Skill。

仅查询地点、门店、景点、活动、营业规则、价格或交通事实时，使用 `yjx-life-query`；将资料组织成有完整游玩思路、可浏览维护的攻略时进入本 Skill。基础攻略默认包含不绑定具体日期的典型串联动线草案；是否进一步编排绑定具体日期、车次与钟点锚点的单次日程，取决于用户本轮要求。

本 Skill 不负责报名、预订、付款或公开分享。保存行程、地图或 Notion 页面需要用户对该写入范围的明确授权；已经明确授权的同一任务内更新可以继续执行，但不扩大到订单、付款或分享。

## 工作流程

### 1. 确认旅行任务

先确认交付目标是构建基础攻略、编排单次具体日程、完善既有资料，还是从旅行当前进度调整后续安排。制作攻略先读 [攻略资料与呈现](references/guide.md)，据交付用途向 `yjx-life-query` 请求来源摘录、体验评价、经验避坑和可用图文。构建基础攻略时，完成来源查询与结构化沉淀后进入第 4 节，交付空间格局、精选梯队与典型串联动线草案；需要绑定具体日期与钟点的单次行程时，再读取日期、同行者、交通、住宿、固定车次/预约、预算、体力和排除项，执行第 2、3 节。只询问会改变结果的缺项。

如果事实尚未核实，调用 `yjx-life-query` 获取决定性地点与活动资料。对官方时间、关闭公告、入口、适用年龄、交通和价格区分适用日期、查询日期、计划依据与实际体验；不把搜索摘要当作已核实事实。

完成条件：基础攻略与单次具体日程的范围、待查询事实及需要用户判断的取舍清楚；候选资料已具备片区、主备选梯队与适用条件，未授权的具体日期时刻表不混入基础攻略。

### 2. 形成主线和备选

基础攻略先围绕核心体验收敛出“主推核心、顺路可选、建议跳过”三层梯队与 1–2 条典型半日/单日串联动线草案。进入单次具体行程编排时，先保留用户明确重视的体验、已购项目和返程/预约锚点，再安排住宿、游览、用餐、休息和转场。主线应能在正常体力和排队条件下完成；备选记录保存在「场所 / 体验项目」或日程数据库中用于替换主线项目，不默认叠加。

安排每一段时同时核对：

- 固定时间、开放窗口、最后入场和返程缓冲；
- 地点之间的真实入口、交通方式、地图估算、计划预留和等候缓冲；
- 同行者的体力、年龄、休息、用餐和临时缩短路径；
- 变更一个项目后，后续路线、住宿、取行李和返程节点是否仍成立。

完成条件：主线、备选、跳过理由、固定锚点和被保留的约束都有依据；删减或替换造成的取舍清楚透明。

### 3. 制作路线和地图

需要地图或路线时，读取 [路线、地图与保存规则](references/planning.md)。基础攻略提供片区位置总览与典型动线的顺路衔接说明（证据不足时用文字交代空间方位与距离尺度，不杜撰未核实的入口或连通关系）；单次行程的分段路线随已确定的本次顺序制作。路线必须对应时间表中的真实起点、终点、途经点和交通方式：多点步行按游览顺序分段，跨点转场使用驾车或公交路线，单点停留提供地点入口；地图总览不代替实际导航路线。用户已经提供、打开或验证过的高德导航链接属于既有交付物，先回读其起终点、模式和结果并保留；高德社区攻略入口是否可读，不影响既有导航链接的存在或交付。

逐条打开或核对路线链接，检查模式、起终点、途经点顺序、入口身份和距离/耗时。园内路线要对照官方园图、封闭范围、单行线和上下客点；高德能算出路线不代表现场一定可通行。无法核实的段落明确保留缺口，不交付成确定可照走的路线。

完成条件：每个需要移动的时间表条目都能找到对应路线或明确说明为什么省略；路线图、地图点位、正文顺序和时间表相互一致。交付回复直接给出主要路线入口，按实际验证结果区分位置总览、导航路线、可维护地图与手机打开效果；缺失项明确报告。

### 4. 形成可使用的攻略

按 [攻略资料与呈现](references/guide.md) 采用**“上层连贯导读 ＋ 下层结构化数据库视图”**双层架构整合内容：

1. **上层连贯导读（建立完整思路）**：正文按“空间与片区格局 → 精选梯队（主推核心 / 顺路可选 / 建议跳过及一句理由） → 1–2 条典型串联动线草案”展开，让读者无需点开多层数据库卡片即可在脑中形成完整游览画面。已要求编排单次具体行程时，再按 [行程攻略交付结构](references/planning.md#攻略交付结构) 以每日时间表为骨架。
2. **下层结构化数据库视图（批量浏览与动态备选池）**：在导读下方嵌入「场所」「体验项目」画廊或分类筛选视图，维护所属片区、主备选角色、适用时段与来源证据，供批量查阅并在旅途变更时按条件快速抽换；禁止仅嵌入几张数据库表而省略上层玩法导读，也禁止把数十条未筛选的原始节目表直接平铺在正文主线中。
3. **阅读面与核验面彻底隔离**：正文只写可执行结论与会改变行动顺序/可行性的关键条件（如“入园先查当日场次再定先后”“含爆破巨响、需预约”）；废除常识性自保免责话术。某项交通、住宿或项目一旦定案或明确排除，正文就地更新为当前有效方案（最多保留一句排除原因），清理失效的多行比价算例、历史询价表及工具/设备报错过程。

完成条件：读者仅读上层正文即可看懂目的地空间格局、核心取舍与推荐串联动线，下层数据库视图支持按片区与角色筛选；单次行程还须说明每天先做什么、如何到达、何时收尾及如何替换。来源与适用条件可追溯，核验过程与免责套话不进入阅读主线。

### 5. 保存与维护

用户明确要求保存或更新时，先读取目标地图、页面或数据库现状，保留相邻内容和既有预订；优先使用已有 MCP 或接口。Notion 页面、数据库和视图使用 Notion MCP，先读取 schema/视图，再局部更新；不默认打开或操作 Notion 桌面应用。

保存基础资料时执行 [资料保存与复用](references/guide.md#资料保存与复用)。使用 Notion 搭建单次行程时，再按 [Notion 行程落盘](references/planning.md#notion-行程落盘) 保留结构化记录和每日视图。写入后回读本轮涉及的视图、记录、关联与链接；结构性改写前清点数据库和子页面，保留未包含的内容。

发生计划变化或现场临时调整时，从用户指出的当前节点继续：优先从已收集的「场所 / 体验项目」数据库中筛选同片区、符合当前营业时段与体力/适龄硬条件的备选记录替换，同步更新上层正文动线、时间表、路线入口、数据库记录的主备选角色及返程缓冲；定案或明确排除后同步清理正文中的旧比价算例与作废方案。不要只追加一条“更新说明”，也不要为补偿失败覆盖原始攻略。

完成条件：保存后的页面/地图刷新或重新读取仍包含指定修改，相关链接和顺序一致，未授权的原始资料没有被改动；部分失败时分别报告已完成和未完成。

## 最终验收

交付前按本轮范围检查：

- 是否已提供空间片区格局、有主次取舍的精选梯队和典型串联动线草案，未授权的具体日期时刻表是否未混入基础攻略；
- 页面是否具备上层连贯导读与下层结构化数据库视图，未退化为“只有数据库嵌表而无正文导读”或“数十行原始表无筛选平铺”；
- 地点与体验是否有具体内容，配图是否按来源处理，经验避坑是否保留情境、信息性质与来源；
- 正文是否已清理常识性免责套话、已作废的历史比价算例及设备/工具调试报错记录；
- 已保存的摘录是否可独立读取，完整字幕是否仅在需要时加载。

涉及行程、路线或地图时继续检查：

- 每个日期是否只显示自己的主线安排，备选是否没有混入主线；
- 每个固定车次、预约、开放窗口和返程锚点是否能在时间表中找到；
- 每条路线起点、终点、交通方式、地图估算和计划预留是否一致；
- 地图点是否是真实入口或明确标注为片区参考，未把 URL 字段误当作地图坐标；
- 正文、数据库、路线图、地图和附录是否互相指向当前版本；
- 是否仍有“演示版、待补、未定、候选淘汰、用户/本人”等制作语言或残留旧路线；
- 原始参考攻略、未授权页面和订单状态是否保持不变。

未满足验收条件时，继续调查和修正相关范围，不把页面成功打开或一次写入成功当作交付完成。
