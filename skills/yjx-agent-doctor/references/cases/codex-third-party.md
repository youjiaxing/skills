# 真实事故复盘：工具暴露、工具格式与子代理消息

来源及最近验证时间：2026-10-18至25日的实际Codex故障调查与复核。已移除用户路径、会话ID、业务页面与凭证。这里保留的是既有运行证据和结论边界，不是需要在维护skill时重演的模拟会话测试。

## 现象和环境

环境包含桌面应用捆绑CLI、自定义模型目录、Responses协议provider及中转服务。独立调查使用的捆绑CLI版本为 `0.163.0-alpha.10.2`，PATH中的另一个CLI版本不同。后端实际模型身份没有完整的独立服务记录。

一次已授权的网页路线更新由配置为 `gpt-6.1-sol` 的主代理派给 `deepseek-flash @ high` 子代理。子代理没有执行路线更新，转而读取旧材料、调查其他行程和车票。多次纠正没有改变方向。

同一环境此前还出现过第三方模型调用MCP时被工具运行时拒绝的故障。这两类失败发生在不同边界，修复其中一项不会自动解决另一项。

## 工具格式故障

失败调用把应提交的原始JavaScript包装成JSON对象，运行时报错 `tool exec invoked with incompatible payload`，请求尚未到达业务MCP。

历史处理调整了DeepSeek模型条目的 `tool_mode`，从 `code_mode_only` 转向普通JSON工具调用路径，随后业务MCP读取成功。后来复核发现活动目录中该字段是字符串 `"null"`，不是字段缺省或JSON `null`。此次格式修复前保留了模型目录备份；回滚须根据实际字段差异恢复，而不是套用“删除字段”的口述。

因此保留“工具通道变更后读取成功”这个观察，不将事后口述的“移除字段”当作精确差异，也不把字符串 `"null"` 推荐为其他运行时的标准配置。未进一步定位错误包装最初由模型还是中转层产生。

2026-10-25 在捆绑CLI `0.164.0-alpha.11.1` 上复核，结果与上述旧版本相反。当前运行时把缺省、JSON `null` 和字符串 `"null"` 都解析为未设置，只保留 `code_mode_only`。活动目录恢复该值后，临时新进程在改动前曾成功读取Notion页面；重新核对的事件记录还显示，一次新进程运行完成了Notion搜索和按ID读取，返回的页面标题与目标一致。两个DeepSeek目录条目都做了这项恢复，但 `deepseek-flash-1m` 的验证遇到上游 `503`，因此只能记为未验证。旧版本曾失败、新版本已成功，不能据此宣称任一版本的所有第三方模型都适用同一设置。

## Multi-agent编排动作未注入

2026-10-25 复核了两个新建桌面会话：捆绑CLI为 `0.164.0-alpha.11.1`，provider为自定义 Responses provider，根模型为 `deepseek-flash`，会话记录为 `multi_agent_version=v1`。模型目录当前条目包含 root/subagent 协作提示，但会话的 additional_tools 只有普通工具、Codex App、浏览器和 tool_search，没有 spawn_agent、wait 或 close_agent 动作。两次会话都复现“命名空间/提示存在但无法调用子代理”。

失败会话的启动配置没有显式启用 multi_agent feature；模型目录字段和 [agents] 默认子模型因此只表达了意图，没有让 app-server 注入编排动作。此前尝试把问题归因于 `deepseek-flash`，但没有区分 feature 开关、会话缓存和模型能力，这个解释被后续对照推翻。

同一桌面CLI、同一自定义provider、同一 `deepseek-flash` 和同一算术任务做了两次单变量验收：

| 对照 | 结果 |
| --- | --- |
| 增加启动参数 `--enable multi_agent` | 原生 `spawn_agent` 成功创建 `deepseek-flash` 子代理；`wait` 收到子代理原话 `2`；随后关闭子代理 |
| 在配置 `[features]` 增加 `multi_agent = true`，不再传启动参数 | 新进程同样成功完成 `spawn`、`wait` 和 `close` |

因此已确认根因是 app-server 的 Multi-agent feature 未激活，表现为工具注入缺失；不是 `deepseek-flash` 本身不能作为子代理模型，也不是自定义 provider 在该组合下必然不兼容。修复只增加了 `[features] multi_agent = true`，没有修改模型目录或切换模型。已经启动的旧 app-server 和旧会话不会热加载；必须重启对应进程或创建新会话后验收。

该验证使用了明确的桌面CLI二进制；PATH中的其他Codex CLI版本不能替代这组证据。验证只覆盖当前桌面CLI、当前自定义provider、`deepseek-flash` 和 `v1`，不推广到其他版本、provider、模型或通信协议。

## 模型切换后的工具暴露

同一旅行任务仍在进行的聊天中，主模型从GPT切换到DeepSeek后，页面上持续表现为“Notion MCP没有暴露”。日志显示该模型尝试调用未提供的 `exec` 自定义工具，收到 `unsupported custom tool call: exec`；这不能单独证明连接器失效或Notion授权失权。未重新加载该项配置时，同一会话若已能产生Notion MCP调用事件，就能反证故障来自连接器授权或业务服务，却仍不足以解释最初为何没拿到工具。新聊天、新进程或重新加载工具集合可能改变实际暴露的工具；验证时要先确认当前会话的工具声明，再看业务MCP是否收到请求，不能用一次成功反推故障已经消失。

本轮同时暴露了一次操作失误：修复模型目录时曾用JSON解析后整体序列化重写文件，再压缩成单行，原有排版因此经历两次变化。之后按备份恢复了原文件，只重放目标条目的 `tool_mode`，并核对了行数、缩进、末尾换行和逐行语义差异；活动目录与改动前备份只有两条目标字段不同。模型目录需要新进程重新加载，已经打开的旧聊天及其工具集合不能作为新配置的验收对象。交付配置变更时要保留这一区分，并如实说明格式曾被重写。

## 子代理通信故障

子代理首轮记录明确说明收到的NEW_TASK正文是不透明加密载荷，没有可读任务；后续纠正和恢复消息也不可读。它随后从任务名和旧文件推测目标，造成业务偏移。

两次中断都有成功记录，中间存在主代理主动恢复操作。恢复后的继续执行不能证明中断失效。异常子代理记录中没有业务页面更新接口调用；原本的路线更新也没有完成。

该子模型的目录条目沿用了与GPT类似的v2多代理配置，但“复制模板”只是调查线索。真正支持归因的是接收端不可读记录与隔离对照。

## 已有对照结果

事故处理中，关闭业务工具与写入能力，通过临时会话产生了以下传输验证记录。核验关联工具事件、接收者和实际响应，不只采信主代理最终自报的PASS。

| 目录与发送方配置 | 已有观察 |
| --- | --- |
| GPT父v2，DeepSeek子v2 | 初始任务不可读，接收端返回不透明载荷 |
| 只把DeepSeek接收方改v1 | 仍不可读 |
| 父与子都改v1 | 初始任务传递成功；单凭此组不能确定哪一方起作用 |
| 只关闭 `features.multi_agent_v2` | 仍不可读；本机该feature原本已关闭 |
| 只把GPT发送方改v1，DeepSeek保持v2 | 初始任务及同一子代理的后续消息均成功 |
| 上述配置，接收方改为默认GPT模型 | 初始任务及后续消息均成功 |

先只修改 `gpt-6.1-sol.multi_agent_version`，保留备份并确认仅一处语义差异。随后用户明确选择扩展至所有GPT发送方，新增修改其余四个GPT条目，未修改非GPT模型、其他字段或全局provider配置。

扩展阶段分别指定 `gpt-6-astra`、`gpt-6-astra-1m`、`gpt-6.1-sol`、`gpt-6.1-sol-1m`、`gpt-6-luna` 作为发送方、默认子模型配置为DeepSeek，五组均成功传递初始及同一接收者的后续消息。测试目录与正式目录解析后一致；新进程直接加载正式配置也通过复核。

## 可复用结论及限制

- 工具暴露、工具参数格式与代理通信格式是独立契约。先确认当前会话拿到了哪些工具，再定位格式或业务服务边界；保留已经有当前证据支持的修复。
- 接收者版本不一定决定发送端消息编码；发送方、接收方和feature应分别核对。
- 不可读任务需要停止并报告投递失败，不能从旧业务材料补猜。错误恢复会延长原故障。
- v1在该环境下是有效绕行，同时改变了子代理工具接口；旧聊天立即生效、其他接收模型、其他Agent或网关均未获验证。
- 其他四个GPT发送方只验证了修改后的成功路径，没有逐个证明其原v2配置必然失败。此次扩大范围依据用户选择，不是已证明所有GPT存在同一缺陷。
- 已有真实运行结果不能证明本skill提示词会可靠指导未来Agent，也不构成未来第三方模型的兼容性保证。

## 新环境适用性与恢复

预检工具格式时，核对当前运行时实际声明的输入schema、该模型接入路径及当前支持证据；预检工具暴露时，核对模型切换后的会话工具集合及实际MCP事件；预检代理通信时，核对发送方协议、第三方接收路径和消息是否能在接收端被解释。仅发现 `code_mode_only` 或v2配置时，保留为待验证风险，不直接建议字符串 `"null"` 或批量切换v1。

若当前证据证明相同失配，可在会话修复授权内选择最小工具通道或发送方版本调整；先确认候选值受当前运行时支持，并评估工具接口变化。历史通信修复以模型目录备份及精确字段差异为恢复依据，撤销时只恢复目标条目，避免覆盖后续修改。

模型目录通常需要重新启动运行时加载；历史会话和子代理可能仍保留原工具集合或协议。该事故以新进程、新任务验收，不保证恢复旧聊天立即生效。当前环境已能正确处理相关工具或消息时，本案例不构成继续修改的理由。
