# 旅行行程制作

负责把查询结果和用户已知条件组织成可执行的旅行行程或正式旅行攻略。它处理单日多站、多日旅行、已有攻略完善、旅行中计划调整，以及与行程对应的路线、地图和资料维护。

地点、活动、价格、营业、交通和来源事实由 [`yjx-life-query`](../yjx-life-query/SKILL.md) 查询与核验。本 Skill 可以请求这些查询结果，再负责规划、组合、落盘和验收；不要在两个 Skill 中复制或分叉来源核验规则。

## 触发边界

当用户要“制作攻略”“安排这趟旅行”“把这些地点排成行程”“完善已有攻略”“根据变化调整后续行程”或交付时间表、分段路线、旅行地图时调用本 Skill。

仅查询一个地点、门店、景点、活动、营业规则、价格或交通事实时，使用 `yjx-life-query`。查询结果中包含路线材料，不等于已经形成行程；只有用户要求组织成有顺序的旅行计划时，才进入本 Skill。

本 Skill 不负责报名、预订、付款或公开分享。保存行程、地图或 Notion 页面需要用户对该写入范围的明确授权；已经明确授权的同一任务内更新可以继续执行，但不扩大到订单、付款或分享。

## 工作流程

### 1. 确认旅行任务

先确认交付目标是新建行程、完善攻略、调整已有计划，还是在旅行中从当前进度继续。读取对话中已有的目的地、日期、同行者、交通、住宿、固定车次/预约、预算、体力和不希望安排的内容；只询问会改变方案的缺项。

如果事实尚未核实，调用 `yjx-life-query` 获取决定性地点与活动资料。对官方时间、关闭公告、入口、适用年龄、交通和价格区分适用日期、查询日期、计划依据与实际体验；不把搜索摘要当作已核实事实。

完成条件：固定约束、待查询事实、用户仍需判断的取舍和本轮交付范围彼此清楚；简单查询已转回查询 Skill，不继续制作无关攻略。

### 2. 形成主线和备选

先保留用户明确重视的体验、已购项目和返程/预约锚点，再安排住宿、游览、用餐、休息和转场。主线应能在正常体力和排队条件下完成；备选用于替换主线项目，不默认叠加。

安排每一段时同时核对：

- 固定时间、开放窗口、最后入场和返程缓冲；
- 地点之间的真实入口、交通方式、地图估算、计划预留和等候缓冲；
- 同行者的体力、年龄、休息、用餐和临时缩短路径；
- 变更一个项目后，后续路线、住宿、取行李和返程节点是否仍成立。

完成条件：主线、备选、固定锚点和被保留的约束都有依据；删减或替换造成的取舍没有被隐藏在默认安排中。

### 3. 制作路线和地图

读取 [路线、地图与保存规则](references/planning.md)。路线必须对应时间表中的真实起点、终点、途经点和交通方式：多点步行按游览顺序分段，跨点转场使用驾车或公交路线，单点停留提供地点入口；地图总览不代替实际导航路线。用户已经提供、打开或验证过的高德导航链接属于既有交付物，先回读其起终点、模式和结果并保留；高德社区攻略入口是否可读，不影响既有导航链接的存在或交付。

逐条打开或核对路线链接，检查模式、起终点、途经点顺序、入口身份和距离/耗时。园内路线要对照官方园图、封闭范围、单行线和上下客点；高德能算出路线不代表现场一定可通行。无法核实的段落明确保留缺口，不交付成确定可照走的路线。

完成条件：每个需要移动的时间表条目都能找到对应路线或明确说明为什么省略；路线图、地图点位、正文顺序和时间表相互一致。交付回复直接给出主要路线入口，按实际验证结果区分位置总览、导航路线、可维护地图与手机打开效果；缺失项明确报告。

### 4. 形成可使用的攻略

面向家人或同行者时，按日期组织页面。每天以当天时间表为骨架，写清从出门到回程的时段、活动、交通、通勤时间、缓冲和行动提醒；把演出、设施、开放时间、年龄/身高限制和替代项目放入可筛选资料；把影响当天行动的路线和地图放在对应日期附近。旅行体验和吃喝推荐优先查小红书、B站及高德社区分享攻略，再用高德 POI/路线核对身份、地址和动线；运营方/政府来源核动态规则，媒体、榜单和其他平台只补足明确缺项。用户提供的帖子或视频是必查起点但不是攻略范围上限；其中每项有辨识度的吃喝推荐都要进入“具体门店”“现场按品类找”“有依据的替代”或“明确跳过”之一，并把最值得吃什么、在哪找、何时去写进当天主线和时间表，不让来源清单或景点安排挤掉吃喝决策。未读到社区原文或视频完整内容时，标为发现线索并写明读取范围，不将搜索页、卡片、简介或 AI 汇总当成已核实体验。

攻略只呈现当前安排、必要依据和现场可执行的调整方式。查询过程、候选淘汰推理、制作过程语言和与当前安排无关的旧方案应留在折叠资料或查询记录，不放在家人直接阅读的主线中。

完成条件：同行者无需阅读对话即可知道每天先做什么、如何到达、何时必须收尾、出现变化时替换什么；未核实内容和条件性建议都有明确标记。

### 5. 保存与维护

用户明确要求保存或更新时，先读取目标地图、页面或数据库现状，保留相邻内容和既有预订；优先使用已有 MCP 或接口。Notion 页面、数据库和视图使用 Notion MCP，先读取 schema/视图，再局部更新；不默认打开或操作 Notion 桌面应用。

使用 Notion 时，日程、节目和地点保留为数据库记录，每日正文嵌入当天视图；写入后回读视图过滤、行数、排序、关联、路线和地图点位。结构性改写前清点数据库和子页面，避免覆盖未包含的内容。

发生计划变化时，从用户指出的当前节点继续：保留已完成或已走过的内容，更新受影响的后续条目、路线、地图、住宿/取行李安排和返程缓冲。不要只追加一条“更新说明”，也不要为补偿失败覆盖原始攻略。

完成条件：保存后的页面/地图刷新或重新读取仍包含指定修改，相关链接和顺序一致，未授权的原始资料没有被改动；部分失败时分别报告已完成和未完成。

## 最终验收

交付前逐项检查：

- 每个日期是否只显示自己的主线安排，备选是否没有混入主线；
- 每个固定车次、预约、开放窗口和返程锚点是否能在时间表中找到；
- 每条路线起点、终点、交通方式、地图估算和计划预留是否一致；
- 地图点是否是真实入口或明确标注为片区参考，未把 URL 字段误当作地图坐标；
- 正文、数据库、路线图、地图和附录是否互相指向当前版本；
- 是否仍有“演示版、待补、未定、候选淘汰、用户/本人”等制作语言或残留旧路线；
- 原始参考攻略、未授权页面和订单状态是否保持不变。

未满足验收条件时，继续调查和修正相关范围，不把页面成功打开或一次写入成功当作交付完成。
