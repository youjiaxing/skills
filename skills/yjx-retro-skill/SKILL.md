# yjx-retro-skill

由用户手动触发。主会话主持复盘，从本次实际损失与用户每一次纠正行为出发，寻找值得修改的 skill 问题与 Agent 协作体验改进点，而不是对指令逐条挑错。默认只调查并提出建议；修改、安装、提交 skill 或操作外部系统属于另行授权的实施。

## 1. 确定证据范围与分工

默认复盘当前会话中已完成的实质任务，截止本次复盘调用前；用户指定其他会话或任务时按指定范围。区分多个任务及其依赖，避免将复盘过程本身混入被复盘任务。

主代理负责理解用户意图、安排调查、综合归因和交付建议。按被复盘任务的原始对话是否仍保留在当前上下文中分流：

- **当前上下文完整覆盖被复盘任务（未被压缩摘要替换）：** 直接将当前上下文中的用户消息、加载的 skill、工具调用与输出作为主要证据，配合对目标 skill 文件、任务产物或 Git 状态的必要只读核验。全程由主代理单代理完成取证、归因、筛选与交付前核查；**不读取 [会话记录取证](references/session-evidence.md)，不查找或读取当前会话的磁盘原始记录（如 session JSONL），不启用取证子代理或独立评审子代理**。即使更早的无关任务曾被压缩，只要被复盘任务本身的原始对话仍在当前上下文中，仍走本分支。不把缺少宿主显式“未压缩”标记当作状态未知；若当前上下文中个别工具输出被截断或局部证据不足，直接记为证据缺口并限制结论范围，不借此回查磁盘会话日志或开启子代理。
- **被复盘任务在当前上下文中已被压缩摘要替换（含复盘前已替换或复盘期间被压缩），或用户指定复盘其他会话：** 当前上下文中仍保留的原始消息与工具结果可直接作为证据；对已被压缩摘要替换的区段或外部目标会话，读取 [会话记录取证](references/session-evidence.md) 定位磁盘原始会话记录并固定截止点，压缩摘要仅用于定位线索。将需要补读磁盘原始会话记录的只读工作交给上下文隔离（`fork_turns: "none"` 或平台等价机制）的子代理，传入本 skill、目标记录定位、用户目标与约束、明确的调查范围及返回要求；子代理分段读取并仅返回带定位的精简证据包，主代理按定位回查关键原文，不把整份日志载入主上下文。若宿主无法使用子代理，主代理说明限制并自行分段读取必要区段。

按本次目标建立轻量时间线与覆盖记录：用户要求、**用户的每一次纠正行为**（包括显式纠偏、推翻或修正 Agent 输出与做法、中途叫停不当动作；普通方向切换先核实是否属于对 Agent 偏差的纠正）、实际加载的 skill、关键工具结果、失败和返工、最终交付及其核验。当前上下文分支直接使用上下文中的消息顺序、工具调用或事件定位；磁盘取证分支使用记录路径与行号或稳定消息 ID。记录已覆盖区段与缺失、截断、仅有摘要的区段。按时间线覆盖任务，再围绕疑点检索；仅搜索错误关键词不能证明已检查整个任务。

完成条件：能定位被复盘任务、实际使用的 skill、已覆盖区段内的全部用户纠正行为和证据范围；无法还原的部分明确标为缺口。本次优化的主责对象限定为实际使用的 skill；超出当前 skill 职责但经核实有价值的通用 Agent 体验问题，按第 3、4 节单列分流。

## 2. 逐次复盘用户纠正与实质问题归因

除从错误、误解、返工、不必要操作成本和影响使用的交付缺口寻找候选问题外，必须对已覆盖区段内**用户的每一次纠正行为**逐一复盘。必要时按疑点只读核验相关产物、原始来源、脚本或外部实际状态，不完整重做任务。读取外部状态仍需现有访问权限；核验不能附带写入或重新执行日志中的动作。

评估用户纠正时遵循这一准则：**并非用户每一次纠正都是正确、合理的，但大概率符合用户偏好。** 将“纠正是否合理”与“是否固化为通用规则”解耦，先结合当时上下文、客观事实与任务目标逐次判定合理性：

- **合理（有道理 / 符合用户真实偏好或当次合理意图）：** 用户指出了真实的执行偏差、理解错位、低效默认行为、过严/缺失门禁，表达了跨场景协作偏好，或结合当次任务情境作出了合理的指令纠偏。所有判定为合理的纠正，均必须进一步追问“当时为什么会走到需要用户纠正这一步，后续如何从机制上避免再次发生”。
- **不合理（受当时信息偏差或事实误判影响）：** 经客观事实与上下文核验，用户在当时信息不完整或误判客观状态的情况下给出的纠正，按其修改会导致错误或退化。
- **证据不足无法判断：** 因上下文截断、外部状态不可考等原因无法核实纠正合理性或因果，保留为待核实缺口，不强行定性。

对每个候选问题及每次合理纠正核实：发生了什么、偏离哪项用户目标或稳定偏好、造成什么实际影响、当时适用的 skill 指令及其职责定位与准入边界是什么，以及如何从机制上避免同类问题再次发生。尽可能核实执行时版本；当前文件和事后 Git 修改不能直接代表当时版本。明确区分以下原因，可记录共同原因：

| 原因 | 处理 |
| --- | --- |
| 目标 skill 缺口、冲突、默认行为与用户高频偏好相反、过严或缺少适用条件 | 分析如何避免复发，检查最小通用修改能否改善同类任务 |
| 跨 skill / 全局协作层缺口（属用户稳定偏好或通用 Agent 体验机制，但超出当前被复盘 skill 职责边界） | 不写入当前被复盘 skill；提炼通用防复发机制，转入第 3、4 节单列的“跨 Skill / 全局 Agent 体验建议” |
| agent 未遵守已有明确规则 | 记录执行偏差；只有证据显示规则难以发现、冲突或无法落实时才进一步建议修改规则，否则作为“合理但无需新增通用规则”结案 |
| 工具、环境或访问限制 | 指出能力边界；仅在 skill 的能力判断或降级流程有问题时建议修改它 |
| 本次任务或单模块特例（单次事故口径、当次临时改主意、单一业务模块的专属字段/协议/局部规则、或随本次修复/结单即极难再触发的问题） | 单次特例不等于用户当次纠正不合理，但直接排除在通用规则修改建议之外，不将个案特征、模块专属清单或一次性防错补丁写入 skill |
| 原因未知或证据不足 | 列明缺失证据及其对判断的影响，不当作已确认缺陷 |

对照已有保护措施和反证，检查问题是否已在后续版本修复。保留有价值的实际经验，但已解决的问题不再重复建议修改。Git 可辅助定位演进，不能单独证明会话因果或优化效果。

## 3. 筛选最小优化与防复发泛化

只有同时具备具体证据、实质影响（或合理的用户纠偏信号）、可解释的机制归因，以及跨场景的泛用复用价值，才进入正式优化建议。一次严重问题或一次有道理的用户纠正即可作为触发信号，不要求反复发生；但任何写入规则的内容都必须通过**去特例化抽象**：先剥离本次会话的业务模块、专属字段/协议名、具体报错值和当次对话表面原话，提炼背后跨模块、跨任务成立的通用防复发机制（如调整默认优先级、前置检查条件、提问/执行时机、导航或门禁边界）。若剥离具体案例后无法成立通用规则，或问题随当前修复/结单即失效，一律按特例剔除，不新增通用规则。

按职责边界将通过筛选的建议分为两条轨道：

- **目标 Skill 优化建议（主责轨道）：** 属于本次实际使用的 skill 职责范围内的问题，针对该 skill 提出最小修改。
- **跨 Skill / 全局 Agent 体验建议（独立分流轨道）：** 虽不属于本次被复盘 skill 的职责边界（严禁塞入当前 skill 造成污染），但经核实反映了用户稳定的协作偏好或通用工作流机制缺口，能够跨任务避免同类纠偏复发。单独提出并指明合适的承载落点（如 `AGENTS.md`、全局配置或对应通用规范）。

优先选择解决机制的最小改动：澄清适用条件、调整默认动作或导航、消除冲突、删减或放宽约束，或为机械步骤补充确定性工具。比较它带来的执行成本、上下文负担、维护成本和对其他场景的影响。区分“无实质收益的表面字眼挑剔或目录整齐偏好”与“曾引发用户合理纠正、能稳定减少协作摩擦的用户偏好”：前者不作修改，后者在去特例化后纳入对应轨道的优化建议。

预期收益是推断，不能表述为已验证效果。缺失证据会改变归因或修改方向时，保留为待核实线索；不要凭不确定性增加通用规则。

## 4. 核查与交付

交付前，主代理核查每项候选（含目标 skill 建议与跨界 Agent 体验建议）的证据、合理性核验、归因、去特例化程度、职责边界及修改影响，解决有证据的反驳与遗漏，剔除仍绑定单次案例特征或局部业务规则的候选。当前上下文完整分支由主代理直接完成核查，不启用独立评审子代理；仅在“被复盘任务已压缩或复盘其他会话”分支下，当主代理认为有必要或当前项目治理要求独立评审时，才按第 1 节的委派方式交给未参与取证或形成建议的评审子代理。

委派独立评审时，在第 1 节的交接信息中补充用户纠正盘点、候选建议、证据定位、覆盖缺口、反证和关键推断。评审者按定位回查必要证据，不只复述取证摘要；实质修订后针对性复审。需要的核查未能完成时，说明缺口和实际核查状态，不声称已验证或适合直接实施；未做独立评审不等于没有做主代理核查。

报告按以下顺序呈现：

1. **任务与证据概况：** 简要说明目标任务、实际使用的 skill、证据覆盖及重要缺口。
2. **用户纠正逐次盘点：** 简要列出已覆盖区段内每一次用户纠正的定位、合理性核验与最终归宿（若本次任务无用户纠正，明确写无）：
   - **转入目标 Skill 优化建议：** 合理且可泛化，属当前被复盘 skill 职责，指向下方具体建议项；
   - **转入跨 Skill / 全局 Agent 体验建议：** 合理且可泛化，属全局偏好或跨层职责，指向下方独立建议项；
   - **合理但无需新增通用规则：** 用 1–2 句话交代防复发评估结论（如已有明确规则覆盖仅属单次执行偏差、后续版本已修复，或仅属当次任务局部特例而不宜泛化固化）；
   - **不合理故不采纳：** 用 1–2 句话说明客观事实反证，解释为何当时情境下的纠正不宜固化；
   - **证据不足待核实：** 说明缺失证据及影响。
3. **目标 Skill 优化建议（按实际影响排序）：** 每项包含：
   - 问题或触发纠正的场景、可定位证据与实际影响；
   - skill 归因、防复发根因分析、反证及仍未确定的部分；
   - 最小修改位置与去特例化后的通用防复发修改方向；
   - 预期收益、成本、适用边界和评审状态。
4. **跨 Skill / 全局 Agent 体验建议（按需单列）：** 仅当存在超出当前 skill 职责但具备跨场景泛用价值的防复发建议时列出，包含问题与证据定位、跨层机制归因、建议落点（如 `AGENTS.md` 或对应通用层）与去特例化修改方向、预期收益与成本。

建议数量由证据决定，不设必须产出的条数。同一根因的多处问题或纠正可合并展开具体修改建议，但用户纠正盘点仍须逐次交代每处纠正的归宿；除用户纠正盘点与单列的跨界建议外，其余未涉及用户纠正且被筛掉的琐碎内部试错仍不逐条列出。将“有证据支持的建议”“已检查范围内没有值得优化的问题”“证据不足无法判断”分开表达，它们可以分别适用于不同问题或区段。

完成复盘不等于授权实施。用户要求修改时，保留证据、范围和待核实事项再进入实施；提示文档采用静态审阅、一致性及包装/链接检查，脚本允许功能测试。不得创建、保留或运行模拟会话行为测试；静态检查通过不证明 prompt 行为可靠，实际收益通过后续真实使用观察。
