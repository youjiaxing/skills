# 验证与测试准入门禁

本文件承载 `yjx-implement` 在 Phase 2–4 的变更分类、测试准入、证据完整性与审查材料规范，避免在主流程重复阐述各分支细则。

## 仅呈现变更与外观自动化

按**实际影响**分类变更，不按编辑了 CSS、DOM 还是前端文件分类。

- **轻量呈现路径**：纯粹影响字体、颜色、间距、装饰和非功能布局的视觉变更，记录 `Test admission not triggered` 与变更范围，走轻量呈现验证；**不**要求 red-green/refactor-green 证据、候选测试枚举或完整的 `No new test` 论证。
- **混合与功能边界**：业务结果、交互状态、权限、键盘操作与无障碍语义仍受行为测试准入约束；即使只改 CSS，只要实际阻断点击、键盘使用或焦点操作，就属于功能变更（验证受影响的用户结果，不冻结视觉机制）。混合变更分别保留行为切片证据与呈现验证记录，互不替代。
- **外观自动化授权**：仅当**用户明确要求**或**适用项目规则明确要求**时，才允许新增冻结计算样式、精确尺寸/位置或像素/截图快照的自动断言；视觉需求、设计参考、品牌规范、已有视觉测试、无障碍/布局标签或 `"stable contract"` 命名本身均不授予该权限。获授权的外观自动化测试仍须满足下方 **Test Value Admission** 全部 4 个条件；若必需检查无法通过准入，报告冲突并保持验证门禁未完成，等待澄清，不静默以浏览器检查替代。
- **既有视觉测试维护**：仅当确认的需求变更导致旧外观预期过时时才更新或退役断言，并说明依据、验证新契约与仍有效的边界；测试失败本身不构成修改断言的理由，维护既有视觉测试也不触发 test-first 准入。

## 行为测试准入（Test Value Admission）

对于受行为准入约束的变更（或获授权的外观自动化），在新建、扩展、实质修改测试/断言或选取既有测试作为变更前证据前，必须评估以下 4 个条件；**全部满足方可准入 diff**：

1. **Pre-change Signal**：新增行为、变更行为或 defect 测试必须在变更前实现上因目标行为缺失/错误而失败；行为保持型重构的 characterization test 须在变更前通过，且会在合理的行为回归下失败。
2. **Stable Observation**：在合适边界断言外部有意义的业务结果或稳定契约，同时受上方仅呈现变更排除规则约束。
3. **Independent Discrimination**：预期结果源自 requirement 或独立 oracle，并能拒绝一种合理但错误的实现。自动测试面向纯业务规则、算法、状态机或可用真实本地协作引擎（本地/内存 SQLite、临时库、真实编译器/链接器、进程内路由）验证的契约。若被测代码主要是调用外部宿主桥接（如 `plus.ios`、StoreKit）、系统 CLI（如 `devicectl`）或原生运行时的薄适配层，必须手写 Mock 模拟外部系统假设行为才能写出单测时，属于**「Mock 自证测试（Mock Tautology）」**，判为不满足本条件。
4. **Maintenance Return**：回归保护收益足以抵偿 fixture、维护、运行与未来更新成本。

补充约束：
- 对属于 Mock 自证测试的薄外部适配层，直接走 `No new test` 并以目标交付面的定向实证作为验证证据，禁止仅为注入 Mock 在生产代码新增包装接口。
- 不进入版本控制交付的一次性探针、诊断或辅助脚本不属于生产行为切片，不进入测试准入也不为其建单测。
- 未修改测试文件但通过准入的既有测试同样属于已准入候选，必须参与 red-green 或 refactor-green 证据路径。
- **`No new test` 适用条件**：仅当**没有任何**新建、修改或既有候选通过准入时有效。必须在相关业务实现前记录：决策结论、被拒候选及理由、已有覆盖、替代性定向验证、以及评审/交付限制（改变证据形式，不豁免验证）。

## 证据路径与顺序门禁

| 变更分支 | 必需证据路径 | 有效信号与允许准备 | 禁止与失败判定 |
| --- | --- | --- | --- |
| 已准入的新增/变更/缺陷行为切片 | **垂直 red-green 切片**：最窄边界定义切片 → 实现前运行确认针对目标失败 → 仅加必需生产增量 → 同测试转 green → 记录命令、结果与顺序 | 允许仅添加使测试可运行的最小声明或显式未实现占位符（不得含待测行为）；目标缺陷本身为 early return 时有效 | 虚构 API 导致编译错、环境/缺依赖报错、无关 panic、或用实现后对旧代码回测冒充 test-first；缺失 red 命令或顺序则门禁失败 |
| 行为保持型重构（有已准入 characterization 候选） | **refactor-green**：记录重构前 green 命令/结果，以及重构后 green 命令/结果（允许合理重组测试，须保持有效覆盖） | 无需为既有正确行为强造 red 测试 | 有效覆盖丢失或缺少前后 green 记录 |
| 行为变更/重构（无任何候选通过准入） | 完整 **`No new test`** 决策 + 执行既有与替代定向检查并披露限制 | — | 因无新测试文件就忽略验证或跳过边界披露 |
| 仅呈现变更 | 轻量呈现验证 + `Test admission not triggered` 与变更范围 | 静态检查 + 目标表面视觉核验 | 要求补全套 `No new test` 论证或强行制造样式/red-green 断言 |
| 规则或用户明示豁免顺序 | **`authorized override`**（仅项目规则或用户明确指令可授权；普通实施指令不算，用户指令不能豁免更高优先级项目规则） | 记录精确来源、范围与替代验证；若要求 `/tdd`，一并遵守其 seam 确认规则 | 将缺失证据伪装成覆盖豁免；缺少有效路径与授权即视为门禁失败 |

**证据完整性（Evidence Integrity）**：禁止为让测试通过而削弱、删减或禁用校验；无法自动化测试的改动执行适用替代检查并披露限制。

## Phase 3 UI 实测与状态破坏防护

- **UI 实测证据**：任何新增或修改用户可见 UI 的变更（含仅呈现与混合变更），运行适用静态检查并在目标交付环境检查实际渲染表面（Web 优先宿主内置浏览器如 Codex 内置浏览器，原生在目标设备）对照项目 UI 真实来源核验首屏布局与可见文案，记录检查页面、状态/视口、结果与限制。截图只辅助检查，不作为持久回归基线或要求像素一致，也不能替代已准入行为测试的必需证据。若浏览器检查无法执行，如实报告缺口及实际替代证据与限制。
- **破坏性状态防护**：任何（交付或临时的）会修改真实设备容器、持久数据库或共享外部状态的命令/脚本，凡使用不熟悉的删除、覆盖或重置参数，须先在隔离临时域（如 `devicectl --domain-type temporary` 或一次性本地克隆）实测验证，不单凭 `--help` 文案推断；写入后核验受保护父容器根目录与核心数据文件保持完整，不只看目标子目录。

## Phase 4 审查材料映射表

向 `/code-review` 双轴（Standards 与 Spec）传递共同 Decision Context 时，除选定方案、主要成本、被拒分支及理由、剩余假设与风险边界外，按实际路径附上对应证据（混合变更分开列出）：

| 路径 | 传递给 `/code-review` 的证据内容 |
| --- | --- |
| `red-green` 切片 | 可定位命令、针对目标的 red 与 green 结果、先红后绿执行顺序 |
| `refactor-green` | 重构前后均 pass 的可定位 green 命令与结果，及有效覆盖保持说明 |
| `No new test` | 完整决策（为何无候选准入）、已有/替代定向验证及披露限制 |
| `Test admission not triggered` | 仅呈现变更范围 + 轻量验证/UI 检查结果与限制 |
| `authorized override` | 授权来源、生效范围与替代验证结果 |
