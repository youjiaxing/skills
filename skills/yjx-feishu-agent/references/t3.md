# T3 Code 接入与来源迁移

T3 接入使用运行中服务的正式 CLI，凭证由 CLI 自行管理。只发送到用户指定的已有 T3 会话，不创建新会话，不绕过 T3 恢复底层 Codex 会话。其他未映射的来源继续走原 Codex 适配。

## 配置与切换

先停止接收器，备份仓库外的 `feishu/bindings.json`；保留其他群、白名单、投递及入站账本。配置顶层 `t3Command` 为原生可执行程序及固定前置参数的字符串数组，按机器提供可选的 `t3BaseDir`。不使用 shell 包装器；Windows 可使用 T3 安装包原生可执行程序及其 CLI 模块，适配器设置 Electron 的 Node CLI 模式。安装更新后先只读核对入口；路径失效时停止，不猜替代程序。

在明确授权的单条群绑定中设置 `threadTargets`：键为已有的来源 UUID，值为 `{ "kind": "t3", "threadId": "22222222-2222-4222-8222-222222222222" }`。示例 UUID 是虚构值。默认绑定 `threadId` 仍为该群明确选择的来源 UUID；旧来源和当前来源可分别显式映射到同一 T3 目标。来源 UUID 是推送/引用登记的身份，T3 目标 UUID 是执行地址，不能混用。

映射只作用于配置它的群；无映射的引用继续按原来源处理。历史投递指纹和消息来源登记不改写。每条新入站在受理时将实际 `agentTarget` 持久化，后续变更绑定不能改变已受理请求的执行目标。别名指向同一 T3 目标时共享目标锁和未决门禁。

执行 `bindings.mjs check --chat <群ID>`，确认返回 `target.transport:t3`、目标 ID 正确、状态 `readable`，再启动接收器。检查只读，不提交任务，不代表真实飞书往返已验收。回滚时先停接收器，恢复已备份绑定并核对，再启动；保留全部最新请求及投递账本。

## 提交与恢复

适配器只调用一次 `thread send <T3目标> - --wait --json`，消息从标准输入传入；忙碌会话排队，不中断当前运行。提交意图先落盘，只有匹配目标、明确 completed 且带最终 reply 的回执才记为完成。CLI 没有暴露幂等请求键；断连、进程退出、回执丢失及人工输入等待均保留未决，不自动重发、不换编号绕过。

使用 `agent.mjs status --request-id <原ID> --refresh` 只读核对；状态查询按请求账本中的 agent 和原目标分派，不随当前绑定变化。T3 CLI show 只能确认当前最新运行的终态：必须以持久化 marker 精确找到唯一用户消息，再核对同一 runId 的最新终态及回答。后续运行已开始、marker 不唯一或历史不足时保留未知，不能用线程当前 completed 证明旧请求完成。

T3 归档目标阻断，不调用 Codex unarchive。当前 CLI 等待首个完整返回，不保证后台委派工作已全部收尾；需要此保证的流程应由目标会话自行汇总后返回。来源已迁移不意味着原卡片未知投递已经恢复，投递门禁继续按 outbound 协议独立核对。
